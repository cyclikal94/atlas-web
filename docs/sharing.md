# Sharing: the policy and defaults editors (WEB-12a) and household management (WEB-12b)

*10 October 2026. UK English. This is the contract WEB-10, WEB-11 and WEB-12b build against. Nothing here is an acceptance claim: the verdict belongs to the independent review, and the evidence is fixture-stage (the task's integration gates BE-Q1, BE-B5 and BE-CH1 have no formal completion record, so `integration_passed` stays false; see "Not claimed").*

## What the pinned contract provides

The vendored contract (`contract-pin.json`: `0.28.0-rc.1` since the merged client baseline; this card was written against `0.27.0-rc.1`, and every sharing path and schema used here is identical in both) already contains the three backend briefs this card names:

* **B5:** `GET /defaults/snapshot` returns `SharingSnapshot { defaults, households }` from ONE database snapshot. `defaults.revision` is the revision of exactly those defaults and household versions. The client stores it as one record and never combines it with separately timed reads.
* **Q1:** a content `edit` requires `expected_policy_version`; a sharing change since then is a `409 conflict` and nothing is written. A content edit never advances `policy_version`.
* **CH1:** `/management-commands`, `/access-commands` and `/commands` take 1 to 20 commands.

Sharing commands (`replace_policy`, `set_defaults`, household commands on `/management-commands`; `grant`/`revoke` on `/access-commands`) are **online-only**: they are sent through the session's stamped client, never queued in the outbox (D-12a-1).

## Public interface

Import from `src/features/sharing` (the editors) and `src/data` (the defaults record and its capture). Nothing else.

```ts
// src/features/sharing
<ResourcePolicyEditor resourceId open onOpenChange onSaved? />   // WF-SHARING-04, any cached resource kind
sharingItemPath(resourceId)                                     // "/sharing/items/<id>": a link instead of embedding
<DefaultsReview draft onClose />                                // WEB-04 §5.7's review (the /sync queue opens it)
SharingBoundary, SharingEnvProvider, type SharingEnv            // a test or a fixture may provide its own env
type SharingApi, type SharingResult

// src/data
useSharingDefaults(): { record, status: "loading" | "ready" | "none", refresh(), boundary(), acquire(boundary) }
captureDefaults(record, kinds): DefaultsCapture                  // { kind, defaultsRevision, defaultsContext, defaultsReview }
defaultsReviewCase, reviewKinds, parseDefaultsContext, TEMPLATE_KINDS and the snapshot types
```

**`ResourcePolicyEditor`** opens on a resource the cache holds (`useCachedResource`), reads `GET /policies/{id}` (owner only; `403` shows "Only the owner can change who can see this", `404` "no longer available") and `GET /households` for labels and the households a grant can name (with its own loading, failure and Try again, read again on reconnect: D-12a-15), shows the effective visibility of the policy as edited, and saves with one `replace_policy` guarded by the policy version it read (never the cache's `policy_version`, which may lag: D-12a-3). It renders its own absent, offline, owner-only, gone, conflict and uncertain states. It knows nothing about any resource kind. `onSaved` receives the receipt's revision; return `false` to keep the dialog open.

**Routes** (D-12a-7; WEB-12b's household routes are in "Household membership (WEB-12b)" below): `/sharing` (the households, the resolved defaults per kind, the item-sharing explanation), `/sharing/defaults?kind=person|field|task|list|progress` (WF-SHARING-03) and `/sharing/items/<id>` (WF-SHARING-04). The directory lookup (WF-SHARING-05) is a view inside those dialogs (D-12a-11).

### Extensions for WEB-11a

WEB-11a needs a QUICK change of one field's audience ("Only you" / "Home · can view") and the same online-only call rules the editors use; these are exported rather than written twice (D-11a-8). The call rules are exported from the index; `applyPolicyChange` is the slice's second public module, imported from `src/features/sharing/apply-policy-change` (only the lazy people screens use it, and a re-export from the index would put it in the entry chunk: WEB-11a review 3, the merged fixture shell's initial budget):

```ts
// src/features/sharing/apply-policy-change
applyPolicyChange({ api, newId }, { resourceId, from: { version, policy }, to, attempt, isCurrent?, admit? })
  // -> { result: { ok: true, policyVersion } | { ok: false, kind: "changed" | "conflict" | "forbidden" | "not_found" | "invalid"
  //                                                            | "uncertain" | "offline" | "not_sent" | "closed" }, attempt }
useSharingEnv, classifyAnswer, classifyThrown, untilSent, samePolicy, toWirePolicy, canonicalBody, nextAttempt, type Attempt
```

`applyPolicyChange` renders nothing. It reads `GET /policies/{id}` (the page's `403` memo of D-12a-13 applies: a refused policy is never asked again), refuses with `changed` when the version is not the one the caller showed, sends ONE `replace_policy` guarded by the version it read under the attempt's key (one attempt per body: after an uncertain outcome the same key and byte-identical body), and reports `ok` only after a confirming read shows the policy asked for, with that read's version (the content step that follows is guarded by it, Q1). A retry after an uncertain send that did commit finds the version moved and the policy already the one asked for: confirmed, never sent twice. `admit` (WEB-11a review 2) is asked with the exact attempt before it may be sent; `false` sends nothing (`closed`), and the caller's identity is checked again just before the send. Tests: `tests/features/sharing/apply-policy-change.test.ts`.

## What a consumer must do

1. **A queued create that relies on implicit defaults captures them** and passes the capture to the outbox in its build:

   ```ts
   const { record } = useSharingDefaults();               // mount it where the create is made: it also starts the read
   build: (bases) => {
     const capture = captureDefaults(record, ["task", "progress"]); // EVERY template kind the command consumes
     return {
       command: { ...body, ...(capture.defaultsRevision ? { defaults_revision: capture.defaultsRevision } : {}) },
       defaultsRevision: capture.defaultsRevision,
       defaultsContext: capture.defaultsContext,
       defaultsReview: capture.defaultsReview,          // non-empty: queued BLOCKED on review, never sent with an omitted guard
     };
   }
   ```

   Which commands consume which kinds (`create_task` → `task` unless its own policy is explicit, and `progress` always; `record`/`start_timer` → `progress`; …, WEB-04 §5.7 items 2 to 4) is the consuming card's decision. An explicit, fully private initial policy (empty `grants` and `exclude_accounts`) removes the dependency on the created item's OWN kind only: `create_person`, `create_field`, `create_list` and `put_field`'s create branch with one then consume no template. **Every `create_task` still consumes `progress`**, whatever its initial policy (its handler always writes the creator's progress policy from the defaults, WEB-04 §5.7 item 2), so its capture always includes `progress` and a never-fetched capture still blocks it on review; an explicit private task policy only drops `task` from that list.
2. **Never omit the guard on a queued create.** With no record ever fetched the capture is `never_fetched` and the draft is queued blocked; a later background fetch does NOT unblock it. Only the person's confirmation in `DefaultsReview` does (WEB-04 §5.7, "fetching a list is not approval").
3. **An edit of a queued draft keeps its review block** unless the build says otherwise: omit `defaultsReview` in an edit (or pass the same list). Passing `[]` clears the block and is reserved for the review's confirmation.
4. **Every authored-text content edit carries `expected_policy_version`** from the cache (`Projection.policy_version`), as Q1 requires. A sharing change since then makes the edit a `version_conflict`; the policy editor warns that queued edits of the item will need review.
5. **Online-only commands use one attempt per body** (D-12a-2): keep `{ key, body }`; after an uncertain outcome resend the same key and byte-identical body; after any edit use a new key. `model/submission.ts` does this for the editors. **A Try again that is not sent proves nothing about the earlier request** (review 3, R8): offline, held back (`not_sent`) or closed, the uncertain attempt is kept exactly as it was (in every editor: the policy editor's `closed` branch forgot it until the design assessment's DA-P1); only a receipt or the server's own refusal of that key and body ends it. Every entry point is admitted at the action as well as on its button (online, writable, not already sending), a Try again included. The household screens (WEB-12b's `households/operations.ts`; WEB-12a's `HouseholdsMinimal` subset was replaced by them with every guarantee kept) have no version to protect a create, so while an attempt is unresolved it sends nothing new (create, invite, accept, decline), and Reload shows the lists again without ending the attempt (a list read is not proof the request cannot still commit). It owns one operation at a time, taken synchronously at the click: an invitation's directory lookup is part of the operation, and its continuation rechecks ownership, identity, the connection and the server's compatibility before sending. The attempt lives in the households page memory: it survives in-app navigation and a `403` remount, never a reload or another tab (Decision H is WEB-12b's D-12b-2, below).
6. **Form recovery (Q4; WEB-14a revision 37):** the policy editor (`sharing-policy:<id>`: the draft and the version it was composed against) and each defaults layer form (`sharing-defaults:<layer>:<household|personal>:<kind>`) are recoverable models (`lib/form-recovery/editor.ts`, codecs in `model/recovery-fields.ts` and `DefaultsEditor.tsx`), as are the households' create and invite drafts. An accepted update saves them; restoring never submits, and Save stays guarded by the restored base version. An uncertain attempt is never replayed by recovery.
7. **One editor per target** (review cycle 1, R1). `ResourcePolicyEditor` is keyed by the displayed identity and `resourceId`: another resource is another editor, with its own read, draft and attempt, and an answer for the previous resource never lands in it. Every sharing read is bound to its target (`useSharingLoad`'s `target`: the client, which is per account and epoch, and the resource or household), so the defaults editor's household layer is read again for a new primary household before anything can be saved for it.
8. **Unsaved input survives the in-dialog sync control and a lost connection** (review cycle 1, R5; ia.md §1.3.3, §3). The sync control keeps each editor's unsaved draft, with the version it was composed against and an uncertain attempt, in this page's memory for the displayed identity and its target only (`retained.ts`); reopening the same editor on the same target shows it again with a note, and Save stays guarded by that version (a policy that moved meanwhile is a conflict, never overwritten); restoring never sends. Cancel, Done, Escape, the close icon and a successful save discard it. Going offline while editing keeps the defaults editor's forms (Save waits for the connection); the policy editor already kept its draft. `SharingEnv.identity` (`account:epoch`) is what kept input belongs to. **What is kept belongs to the editor's session, not to whatever is on screen** (review 2, R5): `retainedSession(identity, owner)` is the policy editor of one resource (`policy:<id>`) or the defaults editor (`defaults`, every layer, household and kind it kept). The sync control suspends a session and reopening resumes it; a dismissal (Cancel, Done, Escape, the close icon, the Close of the offline, unavailable or failed states) discards everything the session owns and ends it, also while its read is still on its way, offline, or on another kind or household. An unmount alone (the page leaves) is not a dismissal. Reload abandons the reloaded target's kept input before it reads, so a failed reload cannot bring it back; a save forgets only its own target. An ended session's late keep or forget does nothing, and another owner's input is never touched. There is one defaults editor (its route): a second simultaneous host would need its own owner name. Kept input lives in this page's memory only: another tab never sees it and a reload forgets it.
9. **A caller that needs a snapshot newer than a moment uses `acquire`** (review 2, R7). `refresh()` may share any read under way, so its answer can predate the caller. `boundary()` marks the moment (a review opening, a change just saved) and `acquire(boundary)` answers with the record of a read issued after it: one under way is shared only if it was issued after the boundary, otherwise a new read is issued at once, and the answer names the record that read fetched (`{ outcome: "fetched", record }`, else `failed`, `offline` or `closed`). The defaults editor's and the households' post-save reads use it. A caller takes a NEW boundary for each moment that needs fresh evidence: the defaults review renews it when the connection returns and on Try again (DA-C1), so a read still under way from before the disconnection cannot become its "Now". This ordering is for the caller's own answer only: the shared record (memory and W14) still keeps the later `issued_at` and accepts an equal one, so two reads issued in the same millisecond replace each other in completion order (design assessment, DA-O1; the stricter cache rule is an open owner decision, not offered here).
10. **A defaults answer is the database's it was asked under** (review 4, R10). `record` is null, and `refresh()`/`acquire()` answer `closed`, when the database the read was asked under has gone (deleted and created again, closed and reopened, or a database opened where there was none) or the controller was stopped since: nothing asked before is shown, captured or written into the replacement. A caller that receives `closed` for the CURRENT identity asks again (the review's Try again does; the automatic read does by itself). With no database at all the defaults are still read into memory; they are never written into a database that opens later.

## The defaults review

Reached from the `/sync` queue's defaults-review rows ("Review sharing"). It shows one "Was / Now" section for **every template kind the draft consumes**: the kinds its captured context holds AND the kinds its block names (`reviewKinds`; review cycle 1, R3). A block can name only some of them (`captureDefaults` blocks only a kind whose household nobody here has seen, and a server refusal names none), but the confirmation replaces the draft's revision of ALL the defaults, so a kind whose audience was known at capture is reviewed too: its audience may have changed since. Each side is shown **principal by principal** (R4): each household the template names with its access (Read or Edit) and its members, each account granted directly with its access, and each exclusion. "Was" is named only from what was captured with the draft (the named households' members and, from the same snapshot, the names of the accounts the template names directly: `CapturedKind.accounts`); "Now" only from the current snapshot. An account neither names is shown by an abbreviated id, never by a name looked up today. "Now" comes only from a snapshot whose request was issued after the review opened: the review's OWN read (`acquire` with the boundary it took when it opened, R7), never a read already under way when it opened, and that snapshot is both the one shown and the one confirmed. An answer that still predates the opening (a clock that went back) is a failure the person can retry, never an endless "loading". Confirm needs the connection and that read (plan §4.6, review 2's connectivity discrepancy): offline it is disabled with "Connect to see the current audience before sending", and back online it is offered again only once the review has read again. The copy is one of WEB-04 §5.7's four cases, and only a draft that was sent and refused is told the defaults "have changed". Confirm calls `DataActions.confirmDefaultsReview` with the row it showed (`reviewed: reviewedOf(draft)`) and a capture of every consumed kind (an edit in place for a draft never sent, a supersession for one refused); Discard removes the draft (dependants become `rejected`, retained). A draft whose versions moved is refused (`rebuild_refused`) and is reviewed from its own screen: the generic confirmation never sends a body on versions it was not built on. **A draft that changed while it was reviewed** (another page edited it, or its review changed) is refused (`draft_changed`, R2): the newer edit stands, still blocked, and the person reviews the draft as it now is; the confirmation never applies to a draft other than the one shown.

## Limits and decisions

* **D-12a-10, demand-driven defaults.** The defaults are read only while a screen uses them (`useSharingDefaults`), not at every boot: no request on the boot path or by a page that never shows sharing. A page that never used them captures from the persisted record, or queues blocked on review (the safe direction).
* **D-12a-11, the lookup is a view.** WF-SHARING-05 is drawn as a dialog over the Sharing page; here it is a view inside the open editor dialog or sheet (same sections, order and copy), so there is never a modal inside a modal.
* **D-12a-12, the editors are full-bleed sheets below the desktop breakpoint** (review cycle 1, R6; supersedes the cycle-0 "one dialog rule"). The accepted tablet frames draw the policy editor as a full-bleed sheet at 834×1112 and 1112×834 (WEB-05.5 `tablet/sharing-portrait.html`, `sharing-landscape.html`, Q14), so the policy and defaults editors pass `sheetBelow="desktop"` to the shared `Dialog`: a full-bleed sheet below 1280 px and the centred 440 px dialog from it. Every other dialog keeps the generic 768 px rule (the default); focus, the in-dialog sync control and dismissal are unchanged. E-SH8 measures both editors at 390×844, 834×1112, 1112×834 (full-bleed: x 0, y 0, the viewport's width and height) and 1440×900 (centred, 440 px wide).
* **D-12a-13, a 403 remounts the protected tree.** Any ordinary `403` closes the protected display while the session classifies it and reopens it (session matrix 3.6.2: 401 and 403 are possibly invalidating), which remounts the tree. A non-owner's editor therefore asked `GET /policies/{id}` again on every remount (measured natively: 173 reads in three seconds, E-SH9). The client remembers a refused policy per account for the page's lifetime and shares a read still on its way, so it asks once. **Any consumer that reads something on mount that can answer `403` must do the same** (or not read on mount).
* **D-12a-14, kept input has an owner** (review 2, R5). Retention is per editor session (`retainedSession`), not per mounted form: the defaults editor's dismissal discards every layer, household and kind its session kept, including forms that are not on screen. Kind switching is unchanged: an unsuspended edit of a kind is not kept when the person switches kind (only the sync control keeps), and a kind kept earlier comes back when its tab is shown again.
* **D-12a-15, revision evidence and editing metadata are separate reads** (review 5, R11). B5's `households` is NOT your membership list: it names only the primary household and the households the RESOLVED defaults name, so a household you are in that no resolved default names (or that only an overridden template names) is absent from it. What the defaults are, what they resolve to, the primary household, capture, the review's Was/Now and W14 use the B5 record only, and nothing is ever added to it. What an explicit template or a policy can GRANT, and the names of the households a template or policy being EDITED grants, come from the editor's own `GET /households` read (`useMembership`): the complete list, separately timed, read when the editor opens online, again each time it comes back online, and on its own Try again; a later read supersedes an earlier one, and nothing about it is stored on the device. Until a read of it has answered, nothing says you are in no household or not in a granted one: adding a household waits (the button says why), a granted household keeps the name the last list gave it or is shown as "A household (name not loaded)", and the policy editor's summary counts it as "couldn't be loaded", never "you're not in". Re-reading the list never touches a form (choices, versions, kept input or an uncertain attempt). The policy editor's member labels come from the same read, separately timed from `GET /policies/{id}`: it says "Household members as last read …" and that the server checks membership live (D-12a-9). The server checks membership on save.
* **D-12a-16, unknown is never absent** (review 6, R12; design assessment DA-M2). A layer's template is known only from a successful `GET /defaults/templates` answer for that very target, and the primary household only from a B5 snapshot. A read that is loading or failed, or no snapshot on the device, leaves it unknown: never "no template" (so never the application's default, which differs by kind: People and Progress name the primary household) and never "You don't have a primary household". The chain, the personal row, the "Inherit household default" choice and the preview come from one resolution (`resolveKnown`): a present personal template resolves on its own; otherwise the primary household must be known, and if there is one its template must have been read. Anything less is shown as what is still missing ("isn't known yet: the household default hasn't loaded"), with nothing highlighted. A NEW save whose outcome is not known waits, on its button and at the action ("Wait until it's known what new records would start as"); Private and an explicit policy at a known base never wait for it, and an uncertain attempt's Try again is always that same operation (same key and body), whatever is known now. The editor's own snapshot read has its loading, failure and Try again; a record shown although that read did not get a newer one is labelled "Shown as last read …" with its own time (a read the session held back at display is reported `failed` by the source while its own read may land a newer record, so the label is used only when the record predates the editor's request). Templates, membership and B5 stay separate reads: nothing makes them one revision, and `set_defaults` guards only the edited template's own version, so a lower layer or the primary household may still change between the preview and the save (an atomic preview would need an API decision). Offline, the households pane shows the households this page last read with THAT read's time, or, before any was read, the households the last snapshot named, said to be only those (an empty one is not "You're not in a household").
* The household UI is WEB-12b's full surface (below); WEB-12a's demonstration subset is gone.
* Copy is proposed (D-12a-8); visual and copy sign-off stay open.
* WEB-09b's production leadership and recovery are in this base (correction of an earlier sentence, from WEB-12a's hand-off of 11 October 2026): after a save the cache's `policy_version` follows when sync runs, and the editor does not depend on it. Its scoped acceptance is not proof that every composed lifecycle or platform check has passed; WEB-08c owns the composed lifecycle work.

## Household membership (WEB-12b)

*6 November 2026. Implements WF-SHARING-01, WF-SHARING-02, WF-SHARING-05's browse mode and Q21 group 2 (signup invitations) against the released contract `0.31.0-rc.1`. Fixture-stage evidence: BE-Q1, BE-Q16 and BE-CH1 have no formal completion record, so the I-SH10..I-SH17 journeys against the released backend are focused real-backend evidence, not integration acceptance.*

**Routes** (D-12b-1), all inside the existing `sharing` route, the screens one lazy chunk (`households/screens.tsx`; the first load carries only route definitions, D-12b-11):

* `/sharing`: header actions **Invitations (n)** (works with zero households; disabled offline, D-12b-12), **Default sharing**, **New household**; from 1280 px the households pane (280 px) beside the detail of the route's household, else the main household if listed, else the first by name; below 1280 px the pane alone. The resolved-defaults summary is unchanged under it.
* `/sharing/households/$householdId`: the detail (beside the pane from 1280 px; alone below it, with "‹ Households" and the page's level-one heading kept).
* Route-addressed dialogs (full-bleed sheets below 1280 px: `sheetBelow="desktop"`, D-12a-12): `/sharing/new`, `/sharing/invitations` (header-level), `/sharing/households/$householdId/{rename,invitations,signup}`. Confirmations (leave, remove, demote, stop using a main household) are small in-page dialogs; their outcome is kept in page memory, so a remount shows it on the detail.
* Public path helpers: `householdPath(id)`, `invitationsPath(id?)` from `route.tsx`.

**Page memory** (D-12b-3, `households/memory.ts`): one memory per displayed identity, dropped the moment another identity asks for its own; nothing in storage, the URL or history. It holds the complete list (`GET /households`), For you (`GET /invitations`), the walk of `GET /invitations/sent`, the active signup invitations, the directory's browse refusal, the single operation owner, the unresolved attempt, each surface's last problem, the form drafts and an issued signup link until Done. Every read supersedes earlier ones of its kind; an answer for an older generation or another identity is dropped. Each screen asks its reads once per mount and on reconnection, never by itself otherwise, so a `403` remount can add at most one read per screen (no loop).

**Why page memory** (the main correctness risk): every manager command a member sends is refused `403`, and a `403` remounts the protected tree before the continuation sees the answer (D-12a-13). The continuation therefore writes into page memory, and the remounted route reopens its dialog with its draft, its problem and the attempt (S-HH7, E-HH4, MU-6301).

**Decisions** (planning, recorded for the reviewer; no new human gate):

* **D-12b-2 Decision H** (unresolved household attempts across lifetimes): the unresolved attempt lives in page memory (in-app navigation and a remount keep it; a reload or another tab does not). Every household command except `create_household` is version-guarded, so a rebuilt duplicate is refused or repeats an idempotent effect; `invite_to_household` also refuses a second pending invitation. A duplicate create would be permanent (a sole manager can never leave), so New household asks first when the complete list has a household of the same trimmed, case-folded name. **Residual risk, disclosed:** a reload during an uncertain create, then a create under a DIFFERENT name, can leave two households.
* **D-12b-4 Sent by you** (Q16): `GET /invitations/sent` is SENDER-keyed, so the section is "Sent by you" and says co-managers' invitations are not listed. The walk follows `next_after` to null (an empty page with a cursor goes on), restarts once on `422`, and stops at 10 pages (2,000 rows) with a note. Statuses are the server's, verbatim; Revoke only on a waiting row of a household you manage (the invitation's version). The header-level dialog lists all of them grouped by household, households you have left included (answers item 3: a non-operational invitation is never relabelled "expired").
* **D-12b-5 Directory modes** (PPL-4): `GET /directory?username=` is always exact, so `DirectoryLookup` gained an OPT-IN `browse` (and `keep`) prop: Search reads `GET /directory` without a query on an explicit Search and filters here (case-insensitive substring, yourself excluded, "Showing matches among the first 100 accounts" at 100). A `403` (directory disabled) is remembered for the page (one request) and the section says "This server finds accounts only by exact username". Without the prop (every WEB-12a, WEB-10 and WEB-11 consumer) nothing changes.
* **D-12b-6/7 Roles**: members see no manager action and a one-line note; the last manager's Leave and own demotion, and a sole member's Leave, are unavailable with the reason and fix. Role loss is learnt from a complete list read (or a `403`, after which the list is read again); manager surfaces then become read-only, the signup screen saying its pending invitations were revoked automatically.
* **D-12b-8 Main household**: from the B5 record only (`primary_household_id`), never inferred from `GET /households`; `set_primary_household` is guarded by B5's `preferences_version`; with no record it waits; a `conflict` re-reads B5 and says it changed elsewhere.
* **D-12b-9 Signup invitations** (Q21 group 2): `GET /account-invitations` filtered to the household; New invitation → `POST`; the link `<origin>/join#t=<token>` (the fragment: R7) in a read-only field with Copy link (the clipboard only on the click; on refusal the field is selected and the person told to copy it) and Done. The link is held in page memory until Done or dismissal (a remount keeps it) and never reaches storage, the URL, history, logs, a recovery context or the announcer ("Invitation link ready to copy"). An issuance whose answer was lost is NEVER sent again: the list is read again and an id new since is flagged. A `429 rate_limited` with an Atlas body is the cap (or the throttle): New invitation waits until the list changes. A revoke whose answer was lost may be tried again (idempotent effect). Below 768 px each row is a stacked card with labelled fields (design-coverage §7). The client cannot count its own 20 (the list includes co-managers' and has no issuer).
* **D-12b-10 Classification**: for household calls only, `503 slice_capacity` is the refusal `capacity` and an issuance's `429 rate_limited` the refusal `limit` (both need an Atlas body); everything else is WEB-12a's `classifyAnswer` unchanged. `call` gained an optional classifier; `untilSent` accepts any result of the same shape (type-only change). **A `capacity` refusal is worded by the command it refused** (revision 1, review 1 F-R1-3): at 0.31 `slice_capacity` is your own 32-household cap for `create_household` and an accepted invitation ("you're already in 32 households"), but for `invite_to_household` it means the RECIPIENT already has 200 pending invitations ("the person you invited already has as many invitations waiting as Atlas allows"); any other command's is "a limit was reached".
