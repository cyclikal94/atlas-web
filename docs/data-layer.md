# The data layer (`src/data/`)

WEB-09a owns the per-account local database, the ordinary delta sync, the draft outbox, the status model that the sync chip and the sync screens read, and the real
ports that the session's account wipe calls. It is the only slice that may touch IndexedDB for account data. WEB-09b supplies what this slice leaves open: leadership
(which page runs the sync engine and the dispatcher), the first snapshot, and recovery. **In production nothing here starts an engine yet**, so the sync chip reads
"Updates stopped", which is true.

This document is written from the code and the tests. Where a statement rests on a test, the test file is named. Where the design or the plan was deliberately
departed from, the departure is listed under "Departures from the plan".

## Public surface

`src/data/index.ts` is the only import path other slices may use (lint rule R15). It exports the UI hooks and provider, the outbox types and
the command and conflict registries, the account-database name function, the deletion-port factory and the status types, and (WEB-12a) the sharing defaults:
`useSharingDefaults`, `captureDefaults`, the snapshot types and parsers, `defaultsReviewCase`, `reviewKinds` and the review's `ReviewConfirmation`/`ConfirmReviewOutcome`. What the **boot path** imports from it is small and
must not reach Dexie: `createDataDeletionPorts` is a static shim that loads the implementation lazily, the UI composition is a dynamic import, and `vite.config.ts` marks
`src/data` modules side-effect free. `pnpm check:artefacts` runs `scripts/check-initial-chunk.mjs`, which fails if Dexie, an engine or a plan is in the initial chunk
(`tests/static/initial-chunk.test.ts` shows the check failing on a seeded violation). A module imported by both the boot path and a lazy chunk is placed whole in
the initial chunk. The shim therefore takes its fallback digests from `model/unreadable-digests.ts`, not `model/local-work.ts`. Taking them from `local-work.ts` carried
the local-work functions and the SHA-256 code into the initial chunk, past the production budget (R61, revision 39).


Lint enforces the boundaries (`scripts/check-data-conventions.mjs`, rules R13 to R18, run by `pnpm lint`, with positive and negative fixtures in
`tests/lint/data-conventions.test.ts`): IndexedDB only under `src/data/store`, `src/session` and the capability probe; `dexie` only in the adapter and the UI; other
slices import only the index; `deleteDatabase` only in `account-database`; `localStorage` only in the write-failure marker; and the plan registry equals the writer inventory.

## One database per account

The database is named `atlas-` followed by the account id (`accountDatabaseName`, the function the session's default port already used, so the default refusal and the real port cannot
disagree). Nothing enumerates by the `atlas-` prefix (`atlas-auth` shares it); every probe is by exact name. Dexie version 1 declared all nine stores, so later slices need
no migration of their own. **Version 2** (revision R6/R3, decision D-23) changes this slice's own store only: a draft's command moves out of its row into a new store, `draft_commands`,
and the `drafts` store gains three indexes (`src/data/model/schema.ts`; the upgrade moves one draft at a time inside the versionchange transaction, and is shown on a database made
by version 1 in three real engines, `tests/e2e/fixture.data-store.spec.ts`, E-A4):

| Store | Primary key | Indexes | Written by this slice |
| --- | --- | --- | --- |
| `cache` | `id` | `kind`, `parent_id`, `[kind+kind_date]` | the delta page commit only |
| `pending_effects` | `[resource_id+local_id]` | `resource_id`, `local_id` | the claim (`markInFlight`), the receipt, the page commit, clearing |
| `drafts` (the HEADER: every field but the command) | `local_id` | `status`, `created_seq`, `[status+created_seq]`, `*depends_on`, `*index_targets`, `review_block.kind`, `retry_state.state` | the outbox |
| `draft_commands` (the BODY: `{ local_id, command }`) | `local_id` | none | the same transactions as the header: enqueue, edit, supersede, the receipt, discard, the page commit; a body never outlives its draft |
| `resource_versions` | `resource_id` | none | enqueue, recompute, the page commit |
| `form_recovery` | `[form_context+tab_instance_id]` | `form_context` | the form-recovery port |
| `sync_state` | `key` (`"singleton"`) | none | the ordinary fields (see below) |
| `cache_staging`, `materialise_sequences`, `reminder_firings` | | | created empty; owned by WEB-09b, WEB-10c and WEB-14b |

**Why a header and a body (D-23).** A command can be large (an import carries up to 1 MiB) and an IndexedDB read returns whole rows, so every scan, count and list of the queue read the bodies of drafts nobody
was looking at. The header is the small row (about 2 KB) that every queue read, dispatch scan, summary, consent count and page reconciliation uses; the body is read for **one draft at a time**, when it is sent, edited or projected. The header gains a derived `kind` so the
registries never need the body. The three new indexes are `[status+created_seq]` (the oldest drafts of one status, in queue order), and two nested key paths that list a row only while it has the object (`review_block.kind`: the reviewing drafts;
`retry_state.state`: the backing-off and the paused). This departs from WEB-04's single `drafts` row (see "Departures"): the record set is the same, only its layout differs. The test double counts the rows each plan reads (`idb.reads`), and every
outbox and engine scenario checks after each settle that no body outlives its draft.

The `sync_state` singleton is seeded with a fresh `incarnation_id` inside the versionchange transaction that creates the database. A database that exists without its
singleton is re-seeded in place and never deleted, so retained drafts survive.

A page obtains a database only through `openAccountData`. Opening an existing database never creates one (an absent database is `absent`); creation happens only while the
may-create predicate holds, inside the session's own per-account `atlas-delete:` lock: this page's identity is that account and no logout or retirement is pending for it. Both are
facts read synchronously, and both fail closed. No code path creates a database after a confirmed wipe (`tests/e2e/fixture.data-wipe.spec.ts`, E-W5, which holds a stale store
handle and fires a late strict write, a draft write and a form-recovery save at the wiped account in three engines). A caller that has gone (`abandoned`, above) starts none either, and `tests/data/runtime-disposal.test.ts` shows it at each phase of an open, over the double of IndexedDB. **The predicate is read at the creating boundary, not only when the call is made (R36, revision 21):** after the wait for the lock, after the listing made under it, in the step that starts the creating open, and once more inside the creating upgrade itself (`permit`, asked by the opener's `populate` hook in the versionchange transaction that would create the database), so a fact that changed while a listing was pending or the request was queued in the engine creates nothing; a refused creation leaves no database and deletes none (removing a database is the wipe's decision), and the answer names the reason (`identity`, `operation_pending`, `closed`, `abandoned`).

## The store port and the plans

Every read and write goes through a **plan**: a read phase that may await only `Reader` methods, a pure `decide`, and an apply phase, all in **one** transaction. A plan
declares its scope, mode, durability (`strict` or `default`) and guards. A response-derived plan carries the `Captured` value taken when its request was issued.

The registered writers (`src/data/plans/*`; `tests/data/plan-inventory.test.ts` (F-S7) checks that the registry equals this inventory):

The Dexie adapter binds every plan operation to the explicit Dexie `Transaction` object (`trans.table`), not to Dexie's implicit "zone". A real engine found why: awaiting a
native `async` function between two requests loses the zone, the later writes then run as separate transactions, and the first transaction commits before the page is finished
(Dexie `PrematureCommitError`, first seen on the 800-change dense page). The conformance suite has a case for exactly that (C-12), which fails on the earlier adapter in all
three engines and passes on the fixed one.

## The commit guard

A response that is applied (a sync page, a receipt, a profile, a device verification) must not be applied after the account it was requested for has moved on. The session's
record (`auth_state`) lives in `atlas-auth`, the data lives in the account's own `atlas-` database, and IndexedDB transactions never span two databases. The commit is therefore
**not inside the atomic commit** of the record's transaction in the literal sense, and what makes it safe is an **ordering**, not a read. The guard is layered:

* **G1** the target database is chosen by the request's **stamped account**, never by `session.identity` at commit time;
* **G2** a synchronous comparison with this page's identity before anything else (a hint: this page's copy of another page's transition is never the authority; it saves taking
  the lock for a commit this page already knows is stale);
* **G5 THE PERSISTENCE HOLD (the authority)**: `session.persistence.hold(account, epoch)` (docs/session.md, obligation 4, revisions 5 and 6), kept until the data transaction has completed or failed. A hold that runs out is **revoked**: the transaction is handed the hold's signal (`RunOptions.signal`, which the store honours wherever the transaction is: queued, reading, applying), the decision refuses once the hold is invalid (G5b), and the lock is kept until the transaction has settled;
* **G2b** the same comparison as G2, repeated at the moment the transaction body decides (found by the scenario matrix: a commit queued behind another transaction was still applied
  after this page had been told of a same-account re-authentication, because the epoch publication was created later and IndexedDB order ran the commit first);
* **G3** inside the transaction, read from the same database: the incarnation, a closing fence, the cursor compare-and-set, the recovery generation, the ownership token and
  the **published epoch mirror** (defence in depth: with the hold it is redundant for identity, and it still protects a deployment that did not supply one);
* **G4** close on transition: when this page's identity leaves the account the service closes its connections synchronously, and when the epoch changes within the account
  it publishes the new epoch, so the first page that learns of it protects every page's later commits.

**The runtime's lifetime (R35, revision 20).** A `DataRuntime` owns the services of one page's provider lifetime, and **its disposal is terminal**: `dispose()` ends every service, stops following the identity and the latches, and makes every later `open` answer `refused/abandoned`; a page that wants a runtime again builds a new one (the provider does on every start). An open that was **pending** when the runtime was disposed belongs to the same lifetime: when it finishes it installs no service, publishes no epoch and lifts no latch, and it lets go of exactly the handles it opened (`store.close()`: that open's own two connections and only their entries in the page's registry), never `registry.closeAll`, because the registry is the page's and a healthy replacement runtime may have opened the same account since. Two layers hold this independently: `openAccountData` takes `abandoned` (read before each listing, native open and creation it would START, and after each native open it has just FINISHED) and the runtime releases the store of any outcome that arrives after its disposal whatever its opener did. Two opens of one account in one runtime keep one service (the later completion hands out the standing one and lets go of its own store). **Stated limits:** a creating upgrade that has begun cannot be taken back, so an abandoned creation leaves the database it made (deleting one is the wipe's decision); a pending request for the wipe's lock stays queued until it is granted or its 20 s bound ends, and is let go the moment it is granted; nothing here is evidence of a physical freeze, a crash or a device.

**The lifetime of an open (R37, revision 21).** An open has a lifetime of its own: it begins when it is asked for, and a **closure** of the account on this page ends it: `registry.closeAll`, or a latch to anything but `open` (a wipe, another tab's deletion or upgrade, the identity leaving). `ConnectionRegistry.generation(account)` counts those closures (per account, only upwards; lifting a latch is not one), an open reads it when it is asked for, and **an open whose lifetime a closure ended neither lifts the latch nor yields a store**: it answers `refused/closed`, lets go of exactly the handles it opened (`store.close()`, never `registry.closeAll`) and leaves the latch as the closure set it. The latch's current value cannot say this: a deliberately authorised NEW open begins while the account is latched and lifts that latch when it finishes, and an earlier open that a closure ended finds the same value. Two layers hold it independently, as for disposal: `openAccountData` (read in the step that starts each native open, after every wait and where a native open has finished) and the runtime (its own reading around `deps.open`, so an implementation that knows nothing of closures cannot undo one; it comes before the identity check, so a wipe's latch is not replaced by the identity's). **The Dexie opener** (`createDexieOpener`) holds its own part: **every connection it acquires is in the page's registry from the moment it exists** (before this, both joined only when the open was over, so a `versionchange` that arrived meanwhile closed nothing, the deletion that sent it stayed blocked, and a second request queued behind that deletion waited for ever), and after each wait it reads the generation, so an open that a closure ended lets go of everything it holds and fails (`StoreFailure("closed")`, which `openAccountData` reports as `closed`). The controller reads `closed` like `abandoned`, as a **failed look** (never an absence), but keeps the healthy runtime. **Stated limits:** a connection whose native request has finished in the engine while the opener has not yet been told (the held completion) is not in the registry until the opener is told, so it closes when the opener next looks (a connection that is not known to the page cannot be closed by it); a creating upgrade that has begun is still not taken back; an opener that ignores `permit` is covered only by the check made in the step that starts the open; nothing here is evidence of a physical freeze, a crash or a device.

A drop writes nothing and changes no `auth_state`. The drop reasons are a closed set: `identity_changed`, `incarnation`, `closing`, `position`, `generation`, `owner`, `epoch_superseded`, `closed`,
and `unverified` (the identity could not be verified in time: the record could not be read, or a settlement held the lock; nothing was applied and nothing is counted, and the engines ask again, paced).

### The persistence hold (what orders a commit against a transition)

> Every change of `auth_state.settled` is made while the writing page holds `atlas-auth` exclusively. A commit takes `atlas-auth` **shared**, reads the durable record under it, and keeps it until its data transaction has completed. So a transition is either committed before the verdict (and the commit is refused, whatever this page has been told) or it cannot begin until the commit has persisted (and is ordered after it). No notice, hint or broadcast takes part.

The hold is one shared Web Lock request and one read at the record (about one IndexedDB round trip), taken for every response-derived commit (`AccountService.commit`); holds coexist, so commits are not serialised
with one another, only with settlements. `unorderedPersistence` exists for a page with no session record (a test world, the raw-store fixture page); production composition passes `session.persistence`, and a static test keeps
it so.

**When the hold runs out (R2, revisions 6 and 7).** The first revision released the lock at the bound (30 s) and left a transaction that was still queued, or applying, able to commit afterwards, on the strength of a verdict nobody vouched for any longer: another page could have settled a
switch, a same-account re-authentication or a sign-out in between, this page was never told, and the old commit came back `applied` (the second revision review reproduced it with a blocking `sync_state` transaction). Now the end of a hold is a **revocation**, in this order:

1. `valid()` turns false and `revoked` fires, synchronously. The store ends the transaction wherever it is (`RunOptions.signal`: a transaction that has not started, is reading or is applying is **aborted** and nothing of it is durable; in the Dexie adapter `Transaction.abort()`,
   reported at once, because Firefox and WebKit deliver the abort event of a transaction still waiting in the queue only when the one in front of it finishes, which conformance case C-14 found in real engines), and the service refuses to start one (`unverified`). The decision of a transaction a store
   did not abort checks `valid()` too (G5b), so a decision made after the revocation writes nothing;
2. the lock is **kept until the transaction has settled** (`hold.track`): an aborted one settles at once, and one that is already committing cannot be aborted and completes while the lock is still held, so it is ordered before any settlement, as an unexpired commit is;
3. only then is the lock released, and a settlement can begin.

The commit that was revoked is `dropped` with the reason `unverified`: nothing was applied, nothing is counted, and the engines ask again, paced. **A commit is `applied` only if its transaction completed while the lock was still held**, so no settlement of the record can be ordered
ahead of it. **Step 2 has no deadline (revision 7).** Revision 6 gave the lock up `persistenceDrainMs` (10 s) after the revocation, and the third revision review's R2 showed that this waived the invariant for the transaction that was already committing: from this page a commit that is still committing (its
data is **not** durable yet) cannot be told from one that is durable whose completion has not been delivered, so when the lock went another page could settle a switch, a re-authentication or a sign-out and the old commit could still land after it, with no later ordering fence, while the store result was
returned `applied`. Nothing on this page can force a committing transaction to end (`abort()` refuses), so the lock is kept until the transaction has aborted or completed, **however long that takes**; `release()` waits for registered work as well. `persistenceStallMs` (10 s) after the revocation, work that is still unresolved is
**traced** once (`persistence.stalled`); it releases nothing. The cost is availability: another page's settlement waits for its own bound (`lockWaitMs`, 20 s), gives up (a sign-out is refused as `closing_write_gave_up`, a sign-in or switch reports `lock_timeout`) and is retried, and is made only after the commit ends or the holding page is closed or
reloaded (a Web Lock does not outlive its page): a stall can delay a sign-out or a switch, never reorder one. The hold's bound is also a deadline for the whole commit, queue wait included, so it is kept above the apply watchdog
(`syncApplyWatchdogMs`, now 20 s, which measures the apply alone): an overrun must meet the watchdog, which steps the page size down, before the revocation, which only retries.

**Limits, stated plainly:** the data transaction is not inside the record's transaction (nothing can make it so); an invalidation (`401`, `credential_mismatch`) adds a fence without changing `settled` and is not covered by the
hold (it is classified by the page's own copy and stamp-checked where it commits); and a hold that cannot be had within 20 s is `unavailable`, never a verdict about identity.

How it is shown (`tests/data/commit-guard.test.ts`, F-S1 to F-S8 revised, over `tests/support/data/stamp-world.ts`, whose gate now runs the kernel's own `openHold`, and `tests/data/commit-guard-expiry.test.ts` for a hold that runs out): every transition of the runner (a switch, a re-authentication, a sign-out, a wipe, by this page or another) is settled under the exclusive lock, at four positions
relative to the commit (before it, queued behind a blocker, executing, completed), with this page's notice delivered, delayed or never, the commit's completion `normal`, `late` (the data is durable and only the completion event is held back past the hold's bound and the stall report) or `unfinished` (the engine is still committing: the data is not durable yet and lands only after both bounds), and five database states. **No stale commit is applied in any cell**, including
every cell in which the page is never told; the reviewer's reproduction (`other_signout`, `before_g2`, no notice) is dropped. The same matrix WITHOUT the hold is kept as the contrast: the residual window below is what the hold closes, and it is asserted to be exactly
that set. The premise itself is a property of the session's fake platform on every scenario of every suite (docs/session.md), and E-P1 shows the shared and exclusive requests ordering correctly with real Web Locks and the real `atlas-auth` store in three engines.

### What the layered guards alone leave (without the hold)

> A response decoded under `(A, e)` may still be applied to A's own database after another page has committed a transition away from `(A, e)`, **if and only if** no page of this browser has yet (a) closed A's connection (the identity left A), or (b) published the new epoch to A's database (the epoch changed within A), and this page has not yet been told. The window ends at the earliest of: this page's notice, the next page's observation, the data transaction's own guard reads.

This is the window that G1 to G4 characterise **without** G5. What could be written in it was limited by construction: A's own server-authorised content, as of the request, onto a cursor that must still match (CAS), into A's own
database, never B's, never a re-created database. Display is gated independently by the session (render permission is by the durable record, not by the data layer). It was a **freshness** question, not isolation or privacy, but it
was still a stale persistence, which obligation 4 does not allow, and the hold closes it. The contrast is characterised by `tests/data/commit-guard.test.ts`, exercised in real engines with stale handles held across a wipe (E-S1 and E-W5), and against the released backend
by holding a real `/sync` answer while the account is switched or logged out (I-S1: the late page is dropped, the cursor is unmoved, and no database is re-created).

## The ports the session's wipe calls

`createDataDeletionPorts` registers the real `AccountDatabasePort`, `LocalWorkPort` and `WipeCoordinationPort` through `browserPorts({ deletion })`, replacing the refusing
defaults of WEB-08a (obligation 1 of `docs/session.md`).

* `exists` answers by `indexedDB.databases()` for the exact name and **rejects** when that call is unavailable, which the session's kernel maps to `retry_later` with
  `adapter_missing` and keeps its ledger entry; it never answers "absent" about data it cannot see.
* `summarise` counts unsynced work: drafts that are `queued`, `in_flight`, `rejected`, `blocked`, `version_conflict` or `operation_conflict`, acknowledged drafts that are
  still held pending the cache or whose outcome is unavailable, and the form-recovery copies (`src/data/model/local-work.ts`). It returns the items and a digest; the logout and retirement dialogs recheck it at
  confirmation, so a count that moved shows "Actually N changes".
* The draft fence is set **before** the network call (`setDraftFence`): from then on a new draft or an in-place edit of a queued command is refused, while form-recovery
  saves are still taken (an unfinished form is autosaved while the logout request is in flight). `setClosing` refuses even those, and the wipe's digest comparison then decides
  whether the person must be asked again (renewed consent) or the deletion may proceed.
* **The durable closing flag is a precondition of a deletion (R12, revision 8).** `setClosing` answers `closing` or `unconfirmed` (`ClosingOutcome`): `closing` only when the transaction that sets `draft_fence.closing` has COMPLETED (or there is no database to close), and only then does it announce `wipe_imminent`.
  It stays TOTAL (it never rejects) but is no longer SILENT: a transaction that aborts, errors or hits the quota, a singleton that is missing, a chunk that did not load, all answer `unconfirmed`, and nothing is announced (a tab that acts on `wipe_imminent` closes and latches, and no tab may observe it while `closing` is still false). Revision 7 swallowed the failure, so the wipe read the live digest and deleted with the flag unset;
  a recovery writer in a page whose broadcast was delayed or absent (the flag, not the hint, is what excludes it) could commit a copy between the digest read and the deletion, and the writer, which does consult the durable flag, found none to refuse it with (the third revision review reproduced it in the double and, with a thrown `DOMException` on the closing write, in native IndexedDB in Chromium, Firefox and WebKit: the late save was answered `saved` and the database deleted).
  The kernel (`WipeService.confirmClosing`) asks up to `closingWriteAttempts` (3) times, the first re-ask at once and later ones after the usual back-off, and treats ANY answer but exactly `closing` (a rejection, `undefined`, the old swallowing shape) as `unconfirmed`. Without the flag it reads no digest, closes nothing and deletes nothing, and reports `retry_later` with the new reason `closing_unconfirmed`: the ledger entry, the draft fence and the work stay, and the next entry
  (a boot's `recoverPending`, a fresh sign-in, a consent answer) repeats step 3a and RECOMPUTES the consent population, so work that arrived in the meantime (a recovery write is accepted until the flag is set: the pre-closing exemption, and it is counted by the digest) is asked about, not deleted. An approved deletion (`deletion_approved`) is held back the same way and completes on the retry without asking again.
  `tests/session/wipe-closing.test.ts` (the kernel over the fake ports), `tests/data/wipe-closing.test.ts` (the real session, the production ports and the production writer over the double: the review's schedule, transient and persistent, abort, error and quota), `tests/data/wipe-coordination.test.ts` and `tests/data/ports.test.ts` (the adapter and the shims), E-W7 in `tests/e2e/fixture.data-wipe.spec.ts` (a thrown `DOMException` on the closing put, in real IndexedDB, in three engines; a brand-new page context as the late writer), mutants MU-101 to MU-107 and, in a real engine, MU-125.
* **An open that FAILS is never an absence (R12, revision 11).** Each port call opens the account's EXISTING database for the duration of one call (`createDexieOpener`, `create: false`, one connection), and the opener answers `absent` only when ITS OWN refusal to create the database ended the open: the `populate` hook, which Dexie runs only inside the upgrade that creates a database (old version 0), refused and set a flag, so the flag proves the database did not exist. The revision-8 fix hardened the closing TRANSACTION; the opener still answered `absent` for ANY `AbortError` raised while it opened without the right to create (and for any on its second connection), and an aborted open REQUEST is not proof that the database is missing (the review injected one for an existing database that held an unfinished form: `summarise` counted zero work with the ordinary empty digest, `setClosing` answered `closing` with no flag written, and `wipe_imminent` could be announced). Every other failure now rejects (`toStoreFailure`), and each caller already turns a rejection into its conservative value: `summarise` answers the unreadable digest, `setDraftFence` rejects (the logout is refused `storage_unavailable`), `baselineDigest` and `liveDigest` answer their unreadable sentinels, `setClosing` answers `unconfirmed` (so the wipe reads no digest, closes nothing and deletes nothing), and the page's own look (`openAccountData`) fails, which the controller keeps as an UNKNOWN (below), so no identity read starts with an empty budget over a database that may hold a pause. `absent` still means, and only means, a database that is not there (`openDirect` of a name that does not exist, the race where it vanished between the probe and the open, an absent account). `tests/e2e/fixture.data-open-failure.spec.ts` (E-C14: the production ports, the page's opener on its first and on its second connection, and a real aborted upgrade of an existing database, in three engines; the faults are NAMED injections of the open request) and E-C11 "an aborted OPEN REQUEST" in `fixture.data-identity-binding.spec.ts` (zero `/me` and `/sessions` requests over a durable pause), mutants MU-347 to MU-349 in a real engine.
* `baselineDigest` returns the digest of the **empty** population (not `null`) for an empty database with no fence, and a digest nothing can equal for work with no fence.
  With `null` the kernel skips its comparison, so work that appeared between the baseline and the closing write would be deleted unasked. This is a deliberate strengthening of
  the plan's wording. The three "unreadable" sentinels (summary, baseline, live) are distinct, because the kernel compares with `!==`.
* The deletion removes the database through `account-database.ts` only, and a failure to list databases, a blocked delete or an error leaves the ledger entry in place; it is
  never reported as success.
* Consent over real data (`tests/data/consent-real.test.ts`; `tests/e2e/fixture.data-wipe.spec.ts` in three engines; I-W1 against the released backend): a confirmed logout
  whose count is unchanged deletes at once, because the person confirmed that count; work that arrives while the logout request is in flight changes the digest and the person is
  asked again, with the choices to keep or delete.

## Ordinary delta sync

### The engine

`createSyncEngine` (`src/data/engine/sync-engine.ts`) performs one step at a time: the local gate and the capture of the request (`request_seq` is incremented when the request
is captured), the quota reserve, the request through `session.api.fetchFor("ordinary", account, epoch)`, then the outcome. Its state is one of `not_started`, `waiting`
(`cache_not_valid`, `paused_by_session`, `offline`), `running` (with `catchingUp`), `idle`, `backing_off`, `paused` and `stopped` (`floor`, `storage_full`, `local_storage`,
`device_capacity`, `unrecognised`, `no_recovery`; a `local_storage` stop may carry `memoryOnly`, below; and EVERY state of an engine that holds an admitted invalidation whose write is outstanding may carry `invalidating`, which hides the cache: see "A failed write of an admitted invalidation" and "The hold"). It is started by `start(ownership)`; **only the fixture harness and tests call it** until WEB-09b supplies leadership.

**Start, stop, start (R8).** WEB-09b uses `start`/`stop` on every ownership change, so progress never depends on an unrelated wake. A restart while an old request is still outstanding coalesces its first tick into the loop
that old step keeps busy; when that step unwinds, the engine (and the dispatcher, audited the same way) **hands the loop to the current generation** at once, so the replacement runs without anything else waking it. It runs only after the old step has unwound
(`maxInFlight` is 1: two requests are never in flight at once), and the old generation's answer is discarded, not applied and not counted
(`tests/data/engine-lifecycle.test.ts`: held response, stop and start, repeated restarts, an ownership change, and no stray tick after a plain stop).

**Resume triggers (R4).** The approved reconciliation table gives a read caller two ways out of a back-off or a pause, scoped to that caller: the browser coming back `online`, and its own explicit "Retry now"; never another caller's success and never time.
For the `sync` caller: the browser's **`online` event** (`EngineDeps.onOnline`, the same input the dispatcher takes; **not** every wake, and not an inference from a reading of `online()`) resumes a back-off or a pause by duration (`resumeReadCallerOnOnline`), and so does an offline-to-online change that is only **read** at a wake (the same signal; one resume, never two); it does **not**
clear a stop that three unrecognised answers caused, which is not a connectivity problem. The event itself counts because an engine that never saw the `offline` before it (a frozen or discarded page) must still resume; a first version of this fix inferred a transition from readings of
`online()` and the released-backend case (a bare `online` event on a page that never went offline) showed that it ignored the event, so it was changed and a unit test now fires the event with no preceding offline (`tests/data/engine-resume.test.ts`). An explicit
**Retry now** clears the caller's pause whichever way it was reached, including the stop for unrecognised answers, which used to fall back into the persisted pause on the first click. That stop is **durable** and shown as `stopped`/`unrecognised` after
a wake and after a reload (the capture gate reads it from the record). Other callers' state is never touched (`tests/data/engine-resume.test.ts`; against the released backend, with **proxy-injected** statuses, the two cases in `tests/integration/integration.data.spec.ts` "REVISION R4": one explicit retry after the unrecognised stop sends a request and the engine returns to idle, and a sustained 503 (the production 180 s) pauses the caller and the browser's `online` event resumes it; the dispatcher's own case is I-O4).

**Local-write stops (R5).** A local IndexedDB write failure (not a quota) of one operation (`page:<cursor>`, `draft:<id>`, `receipt:<id>`) counts in `sync_state.local_write_streaks[operation]`; the third stops **that operation** (reconciliation, validation traces 2 to 4):
the capture gate (sync) and the dispatch window (drafts, receipts) read the streak from the record, so the stop **survives a restart and every wake**, `online` included, and is left only by that operation's explicit "Try again" (which clears that operation's streak and
its fallback marker and no other's) or its own success. When the streak itself cannot be written the stop is immediate and recorded in the account's **fallback marker** (`localStorage`, `atlas-write-failing:<account>:<operation>`, the only `localStorage` use, no
content), which a cold start reads; when that cannot be written either, the stop is held **in this tab only** (`memoryOnly`) and the notice says plainly that it will not survive a reload (`MEMORY_ONLY_NOTE`, proposed copy, not accepted). A restart of the engine with the streak in the record
sends no request and shows the stopped state (`tests/data/engine-resume.test.ts`, `tests/data/outbox-local-stop.test.ts`).

**A stop that only this tab holds lasts as long as the tab (R5, revision 6).** The first revision showed a memory-only stop but did not enforce it: the capture gate read the durable streaks and the markers only, so one unrelated wake sent the page again (the second revision review's reproduction: a failed commit, a failed counter write and a refused marker write, then one subscription wake: a second `GET`). A stop that neither the record nor the marker holds is now kept in the engine (`memoryStops`, keyed by account, incarnation and operation) and offered to the capture gate with the markers (`stoppedOperations`), so it is operation-scoped exactly as they are: it stops the page it names, not a later cursor. It survives every wake, `online` event, visibility change and nudge, **and a stop and a start of the engine** (an ownership change in a tab that stays alive: the dispatcher likewise holds those drafts back from its first step, which reads the page's memory of stops with the markers and the record; since revision 31 that memory is the page's and not the dispatcher's, see "One stop, whichever writer holds it"), it still says `memoryOnly` on every wake, and it is lifted only by an explicit retry of that very operation. A **reload** loses it, which is the disclosed limitation (the notice says so); a stop of the capture write itself (`capture`) was, in this revision, lifted by that operation's own success, because the gate was not asked to enforce it; **revision 7 enforces it** (next paragraph). Another operation's success or streak never clears it (`tests/data/engine-resume.test.ts`, `tests/data/outbox-local-stop.test.ts`).

**A stop of the capture write is enforced by the next capture (R5, revision 7).** The failure of `data.captureRequest` (the write of `request_seq` that precedes every request) is counted under its own operation, `capture` (`CAPTURE_OPERATION`), and it stops after three consecutive failures, or at once when its counter cannot be written (the fallback marker, then this tab's memory). Revision 6 enforced the stops of a *page's* commit (`page:<cursor>`) but the capture gate read that operation only, and the engine offered the gate only `page:` operations, so a recorded `capture` stop was shown once and the next wake wrote the sequence successfully and sent a `GET` nobody had consented to (the third revision review's four probes: a durable three-failure stop, a fallback marker, a memory-only stop, and a persisted marker after a reload; each stopped with zero requests and then sent one). Now the capture gate (`captureRequest`) refuses, before the sequence is written, when `local_write_streaks.capture` has reached the bound or the engine's `stoppedOperations` names `capture` (the account's markers and this tab's memory stops, offered to the gate with the page operations; the dispatcher's `draft:` and `receipt:` operations are its own and stop nothing here). It is `local_storage` with `operation: "capture"`, so the explicit retry clears exactly that operation's streak, marker and memory stop. Ordinary wakes, `online` and visibility signals, receipt nudges, a stop and a start of the engine and a reload all respect it (the durable and marker forms survive a reload; the memory-only form does not, the disclosed limitation); only the explicit retry lifts it, because while it stands nothing is attempted, so the operation's own success cannot occur. Below the bound the operation's **own success clears its own streak** (the capture write is a success of `capture`, in the same transaction), so failures that are not consecutive never accumulate to a stop, and no other operation's success or retry touches it. When both the capture write and the page are stopped, the capture's is named first and the page's is shown after its retry (one explicit retry per operation, as the reconciliation's local-write row has it). `tests/data/engine-capture-stop.test.ts` (37 tests: the four probes, every form of the stop against every kind of wake, operation scoping, the bound and the operation's own success), E-C4 in `tests/e2e/fixture.data-sync.spec.ts` (the marker form in the page's real `localStorage` and the durable form in real IndexedDB, each across wakes, `online`, a real reload and the explicit retry, in Chromium, Firefox and WebKit), mutants MU-91 to MU-95 and, in a real engine, MU-99. The memory-only form is shown in the double only: a real engine cannot be made to refuse `localStorage` and IndexedDB together from a test.

**A success ends the operation's own failure state, and the warning is every stop that stands (R46 and R47, revision 26).** `sync_state.local_write_streaks[operation]` counts CONSECUTIVE failures of ONE operation, so that operation's own success, or its explicit abandonment, ends it, whoever saw the failure. Revision 25 ended it in a second write that only the facade that had seen the failure made (an in-memory `failed` set gated it): after a reload a successful retry of the same save left the durable count or the fallback marker standing and the dispatcher left the saved draft alone; `discard` and `supersede` never ended it at all; the dispatcher's read of the queue never ended its own count (three isolated aborts between successful reads stopped it); and a `recordFailureOfSend` that landed left a prior `receipt:<id>` count in place. And "Try again" for one draft took the shared warning down although another draft was still stopped, and matched operations by the END of the string (`draft:ba` answered to `a`). Now: (1) **in the same transaction as the write** (`withoutStreaks`, `plans/outbox.ts`): `enqueueDraft` and `editQueuedDraft` end `draft:<id>`, `supersedeDraft` ends the replacement's `draft:<id>` and BOTH operations of the draft it abandons (the counter of a replacement that took the end of the queue is written in the same `sync` row), `discardDraft` ends both operations of the draft (also when the draft is already gone, `not_found`: nothing remains to fail; a refusal for any other reason abandons nothing), `markInFlight` ends a BELOW-BOUND `draft:<id>` count (it refuses a draft that stands stopped and ends nothing of the stop, R46 revision 28) and `recordFailureOfSend` ends `receipt:<id>` (`admitReceipt` and `recordOutcome` already did), and the repeat of a save or a supersession that had already landed (a duplicate) ends them too. A transaction that does not land ends nothing: a success that cannot be written is a FAILURE and counts. (2) The page then ends what only it keeps (`ended` in the facade, `succeeded` in the dispatcher for a receipt's write; a landed CLAIM no longer calls it, revision 28): the operation's fallback marker and its memory stop, exactly the operations named, whether or not it saw them fail; a marker that cannot be removed is still a stop and the next success or retry tries again. (3) The dispatcher's successful read of the queue (`readDispatchWindow` reports `queueFailures`) ends the `queue` count, marker and memory stop, and releases the drafts it had stalled whose stop has since ended (`reconcileStalled`: the stops that stand are those of the record, the markers and `memoryOnly`; a release reads the queue again at once, because the window that was read still held the draft back, and an edit wakes the dispatcher as every other save does). A retry takes it down at once only when nothing else is known to stand (the person's "Try again" has always done so), and the look then puts it back if a stop remains. With two drafts stopped, "Try again" for one leaves the other's stop and the shared warning, after a reload as well; `deriveNotices` takes the facade's flags and the dispatcher's state, each following its own records. A stop of a draft's operations that a cascade rejected (a dependant of a discarded draft) is not the discarded draft's own: it ends with that draft's own dismissal or success, or with "Try again" for every draft. **One stop, whichever writer holds it (R46 and R47, revision 27).** Revision 26 ended an operation's failures in the transaction that wrote them, and ended its marker, but the stops that only the tab's MEMORY held (neither the record nor the marker could hold them) were kept by each component alone: the facade's `memoryOperations` and the dispatcher's `memoryOnly`. A facade composed with a dispatcher and given no markers shares the dispatcher's record (`dispatcher.stops`); one with neither has its own. A database change another tab announced is heard while a stop is shown or unsure, and a marker another tab sets or removes when the outbox's own markers (a draft's or a receipt's) are not what the facade last saw (the markers' feed, R15; the feed names a KEY and a marker change carries nothing else, so the facade compares the set of its own markers and a marker for a page, a capture, an invalidation, the queue or another account costs no read, which the existing E-C8 cases assert). **A stop admits no send, and an unreadable marker is unknown, not empty (R46 and R47, revision 28).** Revision 27 made one stop of the union of three records and made the dispatcher's queue read honour it. **A failure is ended by its own key, and by the version it was seen at (R52 and R53, revision 32).** The review of revision 31 reproduced two ordering defects that the instance names left. (R52) A marker was one key whose value named the failure; a success compared the value it had witnessed with the value it read and then called `removeItem` of the shared key. `localStorage` has no atomic compare-and-remove (the HTML Standard advises authors to assume no locking across agent clusters), so another page's NEWER failure could replace the value between the two calls and the removal deleted it: on a direct retirement, on a retirement that was OWED and settled by `probe` or `witness`, and on one settled by `inspect` (all nine interleavings failed, in three engines, over two real pages). Ending a failure is `removeItem` of the exact key a witness named: whatever another page wrote between any two calls has a key of its own and cannot be reached, and nothing compares a value first. **A wake that arrives while a step runs is remembered, and honoured when the step ends (R22, revision 10).** Revision 9 made the step's own schedule always stand, and assumed that the step had absorbed every wake that arrived meanwhile. It had not: a step reads its facts (the service, the identity, connectivity, the durable queue) at its start and then waits for a response, a decode or a commit, so a wake that arrives after that read is news the step does not have, and a step that ends `event` sleeps until the next one. The review's two schedules, run through the production implementations: the dispatcher's read of an empty queue is held, a draft is saved through the public `outbox.enqueue` (saved, and its wake delivered), the old read is released, the dispatcher is `idle`, and an hour later the draft is `queued` with zero sends; and the sync engine's response body is held while the same account moves from epoch 1 to 2 and its eligibility wake is delivered, the stale page is dropped, the engine is `waiting / paused_by_session`, and a minute later there is still the one request. The rule (`src/data/engine/pending-wake.ts`, applied by `settle` in each engine) is narrower than the revision-8 `rerun` loop, which re-ran the step whatever it had decided and so skipped a back-off:

* **the wake is remembered, not acted on** (a latch of one boolean and the last signature seen; every step begins by clearing it, so an earlier run's wake is never a later run's; a `timer` and a `start` are not wakes);
* **when the step ends**, the sync engine evaluates again only where the step left **nothing scheduled** (`event`): a back-off after a failure, the idle poll and a paced retry are deadlines and STAND (so `online` during a failing request costs one request, after the back-off, never two, and a wake never ends a back-off early: that is `online` and "Retry now", which resume the caller in the record). The dispatcher evaluates again whatever the step decided (eligibility is per draft: `blockedUntil` and the durable retry state, and one draft's back-off never blocks another's), and begins the queue again from its oldest draft (`scanAfter`, `fruitlessCycles`), as `wake()` says; the re-evaluation is an ordinary step with a clean latch, so only a NEW wake can ask for another: no loop, one request in flight, one request per `online`;
* **two kinds of wake are told apart**, because only one can be repeated by the step's own work: an explicit act (`signal`: a draft saved, `online`, "Retry now", a nudge, a receipt) counts every time; a NOTIFICATION that eligibility may have changed (`notify`: the session's view and identity, visibility, the API-compatibility store) counts only if what a step reads has changed since it last looked: the signature of the service (account, incarnation, liveness), the identity (account, epoch), connectivity and, for the dispatcher, the compatibility fact. The session publishes a new identity object at every evaluation and the step's own request can be what makes it do so, so a notification that changes nothing is not news and cannot feed itself (a change and its reversal during one step are both news: the step may have read either);
* **a stop the step decided is left only by an explicit retry**: a notification, `online` or a nudge that arrives while a step decides one (`stopped`) changes nothing, and evaluating again would only replace a stop that nothing durable holds (`no_recovery`: the invalidation landed and no recovery job is registered) by the capture gate's own word for the same facts (`waiting / cache_not_valid`), so the state would depend on how many wakes happened to arrive. **Found by E-C6**: the first version of this rule honoured every wake, and the full three-engine run showed twelve failures (the four "explicit retry, then connectivity loss" cases of E-C6 in each engine: after `online` and the nudge that follows a retry, the landed write left `waiting / cache_not_valid` where the spec pins `stopped / no_recovery`; the unit worlds had not shown it). A "Retry now" that arrives during the step IS evaluated (it is the act that lifts a stop), and a receipt nudge is not looked at while the engine is stopped. The stop was never stable against a wake that comes AFTER the step (the control in `tests/data/pending-wake.test.ts` shows it: the gate's word replaces it): this makes the state independent of a wake that happens to arrive during the step, it does not make `no_recovery` durable;
* **a receipt nudge** (a command was accepted: look soon) is the one wake that shortens a quiet wait, because the request that was in flight when the receipt was recorded may not show it: it sets the receipt pace (`syncReceiptMs`) when the step left nothing scheduled and shortens an idle poll to it, and **never shortens a back-off**. It used to be lost: the step's own `schedule` clears the timer the nudge had set.

**A back-off's deadline and the blocking capacity stop stand against every ordinary wake (R23, revision 11).** The production-composition measurement of revision 10 found that a notification did not wait for a back-off, and reported it as not changed; the review (rightly) did not accept that deferral: the wake and nudge entries are the engine's public interface, and R22 itself required that deadlines stand. * **two conditions are HELD:** a BACK-OFF (a failed read: the deadline is the timer the step set, the server's `Retry-After` included) and the blocking `device_capacity` stop. They are the conditions that nothing durable re-asserts: a durable pause, the floor, an unrecognised stop and a local-write stop are held by the record or the capture gate, which every step reads again (a stop of one operation ends when that operation is no longer the current one; a step that finds a pause sends nothing), so they are NOT held here and keep their earlier behaviour;
* **a held condition belongs to ONE service** (`heldUnder`: the account and incarnation it was decided under): when the service ends or is replaced the next wake evaluates again, so a hold never outlives the database it was decided for;
* **while a condition is held**, a notification (`wake`) and a nudge (`nudge`, the receipt's included) neither start a step nor move the timer; the wake is dropped, not remembered, because what ends the hold evaluates from the facts it finds then. The ways out are the deadline (the engine's own timer), the person's "Retry now", and `online` for a back-off (one of the two acts the table allows, one request each; it does not leave the capacity stop, like any other wake). A wake that arrives DURING a step is judged when the step ends, as in R22 (a stop the step decided is left only by an explicit retry; a back-off's deadline stands);
* **an idle, healthy engine is unchanged:** it still starts a step on a notification (the existing meaning of a wake, "eligibility may have changed: look now", which a tab becoming visible relies on) and a receipt still shortens its idle poll. Which notifications an engine subscribes to is WEB-09b's wiring.

**A failed write of an admitted invalidation is retained, retried, and hides the cache (R10, revision 8).** After `410 resync_required` (or `400`/`422` on a sent cursor) the engine commits `invalidateRecoveryPosition`. Revision 7 returned `{when: "event"}` when that local transaction failed: no failure state, no retry, no recovery request, the rollback left `cache_status: "valid"`, `deriveGate` said `open`, and the engine stayed `running`, silent (the third revision review's three probes, abort, error and quota: after ten simulated minutes, one `GET`, no recovery request, an open gate and no notice; drafts present). Now:

* the invalidation is **retained** with the stamp it was ADMITTED under (the epoch, the recovery generation and the position), and the next step retries the WRITE of exactly that, **before** any new request and without asking the server again. Every retry goes through the plan's guards (the cursor compare-and-set, the generation, the epoch), so a position that moved on, a generation that was superseded, an invalidation that another page already wrote or a newer identity DROPS it: a stale invalidating response can never hide a newer valid cache (`tests/data/engine-invalidation-failure.test.ts`, "a stale invalidating response cannot hide a newer valid cache"). Only a drop for the position, the generation or the epoch clears the failure's marker; a drop for the identity or a wipe keeps it, and an `unverified` drop keeps everything for the next step;
* the failure has its own operation identity, **`invalidate:<cursor>`** (`invalidateOperation`, in `model/retry.ts`), and follows the rule of every local write: three consecutive durable failures (`local_write_streaks`) stop it (`stopped / local_storage`, the existing "page not saved" notice and its "Retry applying changes"), at once when the counter cannot be written (the account's fallback marker in `localStorage`, then this tab's memory, which says so); a **quota** failure is not counted (a counter would need the very space that is missing): it stops at once as `stopped / storage_full` with the quota notice, recorded in the same marker, and a wake does not turn it into a different notice. The capture gate enforces `invalidate:<cursor>` exactly as it does `page:<cursor>` and `capture`, so every wake, `online`, visibility signal, receipt nudge, a stop and a start of the engine and a reload respect it (the durable and marker forms survive a reload, the memory-only form does not: the disclosed limitation); only the explicit retry lifts it. The sizing ladder is not moved (no page was applied). A write that succeeds clears its own streak, marker and stop, and a page that commits at the position clears the invalidation's streak at it;
* **the cache stays hidden while the write is outstanding**, whatever shows it: the stop itself (`EngineState` `stopped` with `invalidating`, which `deriveGate` and `deriveNotices` read, so the pure status model hides the cache although the database still says `valid`), the durable streak at the CURRENT position (`SyncFacts.invalidating`: shared with every tab and kept across a reload) and the account's marker for the current position (read by the controller, so a reload that could not write even the streak is still hidden). Both are keyed by the current cursor, so a record left at a position that has since moved on hides nothing. **Revision 9 found that this was not enough** (the review of the fourth revision: the stop's flag and the counter are not the invalidation): see "The hold", below, which is what now hides the cache and which a retry, a wake and the engine's state can no longer forget;
* drafts are untouched, and recovery is requested only once the invalidation is DURABLE (the recovery job needs the generation in the record), so the explicit retry is also what starts it, once.

A transient fault (one or two consecutive failures) is retried at once and recovers with one `GET`, one recovery request and nothing left to report; the review's probes use a single injected fault, so for abort and error they now end `waiting / cache_not_valid`, the gate `refreshing`, "Resyncing", and **no notice, because there is no failure left to report**; a failure that persists shows the notice (the same schedules with the fault kept, in `tests/data/engine-invalidation-failure.test.ts`, and E-C5 in `tests/e2e/fixture.data-sync.spec.ts` in real IndexedDB in three engines: abort and unknown, once and every time, the quota stop, the fallback marker across a real reload, and the explicit retry), mutants MU-111 to MU-123 and, in a real engine, MU-126.

**The hold: what hides the cache is not the counter, the marker or what the engine is doing (R10, revision 9).** The review of the fourth revision reproduced six schedules over the production controller, engine and plans (and eighteen in Chromium, Firefox and WebKit): a stop held in this tab's memory alone followed by an offline wake, and an explicit retry followed by connectivity loss or by a persistence hold that could not verify the commit. In each the database still said `valid`, the retry or the wake had erased or replaced the only record that hid the cache (`retryNow` cleared the streak, the marker and the memory stop and recorded a *success* before the invalidation had succeeded; `step` replaced the stop with `waiting / offline` before it consulted the retained invalidation), and after ten simulated minutes the gate was `open` with no notice. A retry is not evidence that the cache has become valid. Now:

* **The hold.** The first failed write of an admitted invalidation records an `InvalidationHold` in the engine (`SyncEngine.invalidations`, a store of `{account, incarnationId, operation: "invalidate:<cursor>"}`), whatever else could or could not be recorded, and it ends in exactly two ways: the guarded write succeeds (`clearInvalidationRecord`, in the same step as the plan's own transaction clears the streak and says `invalid`), or the position is superseded by an admitted state change (a page that commits at it, a plan that drops the retained write for the position, the generation or the epoch, a capture at another position, a gate that says the cache is already invalid, in the snapshot phase or has no database). It does **not** end on a wake, an offline transition, a retry, a persistence hold that cannot verify the commit, a stop and a start of the engine, or a wipe's `closing` gate (which says nothing about the cache being valid). A restored stop (after a reload: the durable streak, the marker) is adopted as a hold at the first gate that reads it.
* **What hides the cache.** The controller (`createDataEnv`) reads four things, all keyed by the CURRENT position, so none of them can hide a newer valid cache: the database, the durable streak (`SyncFacts.invalidating`, every tab), the account's marker, and the engine's hold (keyed by account, incarnation and position; a leader that detaches takes nothing with it: its holds are carried, with the same key). The engine's own state reports the hold on **every** state it shows (`EngineState.invalidating`, decided once in `setState`: an offline wake, a retry in flight and a paced wait included; `not_started` is no engine and reports nothing), and `cacheHidden` in `model/status.ts` reads it on any state, so a reader of the engine's state alone is right too.
* **A retry lifts the stop; it does not erase it.** For an admitted invalidation's write `retryNow` no longer clears the streak, the marker or the memory stop. It lifts the stop for one cycle (`lifted`, in memory), which the engine offers the capture gate as `liftedOperations` (only the invalidation's own stop can be lifted: the capture write's and a page's are still cleared by their own retry), and the plan that writes the invalidation clears the streak in the same transaction that says `invalid`. A cycle has the bound of every local write, counted from the retry: `localWritePauseAfter` failed writes when the counter can be written, **one** when it cannot or the failure is a quota (stop at once, not counted), and a failed write re-stops it with its notice. A stop and a start of the engine end the cycle; connectivity lost between the retry and its first attempt leaves it lifted and the record intact. Because nothing was erased, a follower tab and a reload still see the record and hide the cache (before: a retry followed by a reload showed it).
* **A first admission that cannot be verified is held too.** When the persistence hold cannot verify the commit of an invalidation the server has just admitted (`unverified`: the session record could not be read, or a settlement holds the lock), nothing is decided and nothing is counted as a failure, but the cache at that position is known to be invalid. Before, no hold was recorded, the invalidation was not retained, the server was asked again at every paced step (14 `GET`s in ten simulated minutes) and the gate was `open`. Now it is retained with its stamp and held, the next paced step writes it without a new request, and it is written when the hold can verify again. Nothing durable records this one (no write failed), so a second tab and a reload cannot know it: a disclosed limitation, and the first step after a reload asks the server again.
* **A detach function belongs to the attachment that made it (R30, revision 14).** `attachLeader` returns the function that detaches the leader it was given, and the controller follows the stores of whichever leader stands now (`leaderOffs`). The function used to cut the subscriptions that stood when it ran, whichever leader they belonged to: attach A, attach B, then run A's function (late, or a second time) and B's engine-state, invalidation, outbox and recovery subscriptions were gone, so a `410` that B admitted while every write of its invalidation failed left the gate `open` over a cache the server had called invalid (the review's schedule over the production controller, engine and plans). The function now acts only while its own attachment is the one that stands, and only once: an obsolete one (its leader was replaced, or it has already run) does nothing, and in particular carries no hold, since the replaced leader's were carried when it was replaced. The attachment is the CALL, never the leader object (the same leader may be attached twice). The carry-forward rules are unchanged. Production still starts no leader (WEB-09b), so this is a defect of the delivered public controller, not of a running sync. `tests/data/ui-env.test.ts` (every store the controller follows, counted by its live subscriptions: late, repeated, late and repeated, the same leader attached twice, a restart of the controller between) and `tests/data/controller-invalidation-hold.test.ts` (the review's schedule), mutants MU-488 to MU-490.
* **A detached leader's hold belongs to the controller, through its restarts, and ends only on evidence (R31, revision 15).** `stop()` and `start()` of one controller are a reversible pair (R29), but `stop()` cleared the carried holds: a leader observed `410 resync_required`, the invalidation, its failure counter and the `localStorage` marker all failed to save, so the leader's memory alone held that the cache was invalid; detaching the leader carried the hold into the controller, and the controller's public `dispose(); start()` then forgot it, exposing the same account, incarnation and position as `open` with no recovery and no newer cache (the review's schedule, over the production controller, engine and plans: 1 failure, 3 passing controls; keeping the leader attached, or not restarting, kept `refreshing`). `stop()` no longer forgets them, exactly as a stop of the engine keeps the engine's own holds. A carried hold now ends only on evidence, from a read of the sync facts that landed (`settleCarried`, the facts being the authority): the database incarnation or the position it was admitted for is not the one the facts name (another cache), or the facts say the cache is no longer `valid` (the invalidation was recorded by some tab, and a later `valid` is a recovered cache that a stale hold must not hide, even when it is named by the same position). A hold of another account is not decided by this account's facts (an account switch without logout keeps what the outgoing account's tab knew, for its return, Q3), and a missing singleton is no evidence either way. A reload loses it with the page, as it always did (the disclosed limitation). `tests/data/controller-invalidation-hold.test.ts` (the review's schedule in every order of detach and restart, restarts repeated, a replaced leader, the position moving on while stopped, the recovered cache, the marker control) and `tests/data/ui-env.test.ts` (the same through the controller's keys: repeated stops and starts, an account visit and its return), mutants MU-493 to MU-497. The incarnation clause of `settleCarried` is a hygiene rule with no observable difference (a hold of another incarnation never matches, so no mutant of it exists: it would be equivalent).
* **An older stamp is let go, not parked.** When the identity has moved to a newer epoch since the response was admitted, the retained stamp can never be applied (the plan's guards refuse it); the engine now lets it go and asks the server again under the current one, with the hold standing meanwhile, instead of parking on `paused_by_session` until some other wake.

What it does not do, stated plainly: a failure recorded **nowhere durable** (the invalidation, its counter and the marker all failed) is held by this tab's engine alone, so a second tab and a reload cannot know it (the disclosed limitation, unchanged; the tests pin it as such). After an offline wake a quota stop is shown again as the generic "page not saved" notice, not the quota one (the hold and the gate are unaffected). A detached leader's holds are carried by the controller for as long as the controller object lives, through its stops and starts (R31); a reload loses them. ### The ownership signal and the issue boundary (R26 and R27, revision 12)

* **A signal's cleanup belongs to the run that installed it.** `start(ownership)` binds an abort handler to its generation (`bindAbort`) and removes it when its run ends (`stop()`, or the next `start`); the sync engine and the
  dispatcher share the rule. The handler clears the CURRENT timer and releases the CURRENT waiters, so an obsolete signal (a restart with a new signal or the same one, a `stop()` between) can no longer end the new run's
  idle deadline or `Retry-After`. A signal that is already aborted when it is handed over is handled at once (it never fires). The listeners on a long-lived signal do not accumulate.
* **A step issues only while it is still eligible.** The last test before `GET /sync` is made in the SYNCHRONOUS code that issues it (`mayIssue`, the dispatcher's own rule: the run stands, the service is live, the page is online and the identity is the
  one the step captured, account and epoch), after the quota read that precedes it. A step whose run has ended returns without publishing (a `running` over the `not_started` that `stop()` published, or a `storage_full` for a run that is gone); one whose
  eligibility moved evaluates again from the facts it finds (`waiting / offline`, `waiting / cache_not_valid`, or a new capture under the new epoch). The same family: the capture read's answer (`gated` or a failure), a refused or failed request and an
  unread `503` body publish and count nothing into a run that is not the one that stands; the dispatcher's queue-read failure and its stamped refusals do the same (the durable `unclaim` of a refused draft always runs).
* Production still starts neither engine (WEB-09b supplies leadership); this is the engines' public ownership interface.

### Bounded processing

A response is processed in two passes that never build the page's object graph (`src/data/scan/`). Pass 1 scans the **bytes** once, validates the JSON syntax strictly, and
records only the top-level fields, each batch's revision, and the byte offsets and node count of every change element. Pass 2 runs **inside** the commit transaction: it
decodes one change at a time from its offsets with a fatal UTF-8 decoder, validates the envelope and the projection's base fields, applies the shape gate, and writes in chunks
of `applyChunk`. Nothing is read up front, and only ids that have local work are remembered (R6, revision 6): as each chunk is written the ids it names are looked up in the pending effects and the tracked versions (`interestingOf`: one `bulkGet` of the versions, and EXISTENCE rounds over the effects with the new `Reader.anyOf`, no read of which returns more than the window; see "The lookup is bounded too" below), and what is kept is one small id-to-word record per id the page names that has an effect or a tracked version, never a row. A page that names nothing of the local work reads none of it. A refusal is a fixed-shape `PageInvalid` with
a stage and a reason from a closed vocabulary; no text of the document is stored or logged. A page that fails anywhere aborts the transaction: nothing of it is durable, the
cursor is unchanged and the same page is requested again (safe because `Upsert` and `Remove` are absolute and idempotent by id).

**The reconciliation is done in windows (R6, revision 6).** The first revision read every pending effect, every tracked version and every draft header matching a version before the page was decoded, so what a page held grew with the queue whatever the page said: 350 independent version-checked drafts
made by the public `outbox.enqueue` meant an empty page read 350 versions and 350 headers together. The page now reconciles in windows of `queueWorkingSet` (100) rows (`plans/reconcile-windows.ts`), each window's writes made before the next is read, in the same transaction as the page
(the plan's `apply` is now handed the transaction's `Reader`, and `Reader.byIndex` takes an `offset`, so a result larger than the window is walked a window at a time):

* **effects** are reconciled in primary-key order (on a final page, the live edge, every effect row is visited so an unmentioned one can be resolved; on any other only the effects of the ids the page names), with the owning draft headers fetched per window. `reconcileEffects` is the same pure function the
  whole-population `reconcilePage` uses, and the order is part of its semantics: a draft's flags move at most once, at its first touched effect, so windowing cannot change a result. A draft that would leave but has another effect elsewhere that still shows an overlay stays (that is asked of the
  `local_id` index, a window at a time);
* **versions** are reconciled over the ids the page names, a window at a time, and "does an outstanding draft still target this resource" is asked of the `index_targets` index a window of headers at a time, stopping at the first that does, so a resource with thousands of settled drafts and one standing is
  still answered correctly with at most a window in hand.

Nothing is capped and nothing is dropped; the result is the whole-population function's, which `tests/data/reconcile-windows.test.ts` holds it to over 90 random queues and pages at window sizes 1, 2, 3, 7 and 100 (final and non-final pages, owners missing, one draft's effects spread over many windows, many drafts on one resource, and mutants that skip the other-overlay
check or reverse the order are caught). `tests/data/commit-page-bounded.test.ts` shows, through the public enqueue, what is in hand: the double now reports the most rows one read call returned (`reads.maxBatch`), and for 350 tracked versions, 250 retained conflicts, 200 x 64 KiB import bodies, 350 settled receipts on a final page and 250 drafts on one resource it never exceeds the window
(the reviewer's empty page reads no version, no draft and no body). This is a statement about what is held, not a heap or out-of-memory measurement. The cost is a lookup per chunk of the page (two requests per 100 changes, none when there is no local work at all) instead of a read of the queue per page.

**The lookup is bounded too (R6, revision 7).** Revision 6 still looked the ids of a chunk up with one `Reader.anyOf("pending_effects", "resource_id", ids)`, and a limit on the number of ids does not limit the number of effects per id: every acknowledged operation that touches one resource leaves a receipt effect (with its display patch) until a page reconciles it, so the third revision review
seeded 350 retained acknowledged drafts and receipt effects on one resource, committed a valid non-final page naming it, and one read returned all 350 rows against `queueWorkingSet` = 100. The lookup (`interestingOf(reader, ids, window)`) is now existence rounds: the versions are one `bulkGet` (one row per resource); an id that already has a tracked version is not asked about again;
the others are asked of the effects index in rounds of `min(window, remaining)` rows. A round that returns fewer rows than it was allowed has seen every effect of every remaining id; a full round was cut short, so the ids it did find are settled and the rest are asked again, and every full round settles at least one id, so the traversal ends in at most as many rounds as there are ids. Limiting the combined result
to one window and stopping would have missed the ids behind the heavy one and is not what is done. Nothing is capped or dropped, the reconciliation that follows is unchanged (still one transaction with the page), and the common case (no id with more effects than a round allows) is one request. What it costs: for an id with hundreds of effects, a few rounds of at most a window each (at most as many rounds as ids with ≥ a window of effects), where the old read was one request of everything; no timing of this was measured on a device.
`tests/data/reconcile-windows.test.ts` ("the lookup ... is bounded too", 5 tests: the reviewer's population, the ids behind the heavy one, every id heavier than the window, a tracked version, 60 random skewed queues at windows 1, 2, 3, 7 and 100) holds the lookup to the exact set and to a window per read; `tests/data/commit-page-bounded.test.ts` ("ONE resource with hundreds of receipt effects": final and non-final pages, with and without a tracked version on the shared resource, 350 effects and 150 other resources, a window of 7, a page that names only other resources, an empty final page, and the rollback of every window on a failure) holds the committed rows to the whole-population function and every store's largest read to the window; conformance case **C-16** holds the double and the real Dexie adapter in Chromium, Firefox and WebKit to the same answer and the same bound (windows 100, 7 and 1); mutants MU-96 to MU-98. This is a read-size counter and source inspection, not a heap or out-of-memory measurement.

**The ordinary invalidation is bounded too (R11, revision 8).** `invalidateRecoveryPosition` still read the WHOLE store of pending effects (display patches included) and built whole-population arrays to clear the overlays, so what it held grew with the retained queue even though the page commit no longer did (the third revision review: 350 retained acknowledged drafts and their receipt effects on one resource, an ordinary `410`, and one pending-effect read of 350 rows against `queueWorkingSet` = 100). The plan now has no prefetch: its `apply`, in the SAME transaction and through the transaction's own sink, walks the effects in windows of `queueWorkingSet` in primary-key order by KEY (not by offset, so what the writes change cannot move the walk) and clears each window's overlays before reading the next (`clearOverlayDisplays`, `plans/reconcile-windows.ts`). Nothing is capped, offline input is not limited and no retained work is discarded: every row is visited and only its `display` changes; a failure anywhere in the walk rolls the whole invalidation back (the cache, the position and every overlay as they were). The guards are unchanged, so a stale invalidation is dropped before anything is read. `tests/data/invalidation-bounded.test.ts` (225 tests: the reviewer's population, windows 1, 2, 3, 7 and 100 against populations of 0 to 301 effects on one and on several resources, the final state against the whole-population function, retention, atomicity and the stale drops), conformance case **C-17** (the double and the real Dexie adapter in Chromium, Firefox and WebKit: the exact final state, no read above the window, and a refusal part-way rolling every window back), mutants MU-108 to MU-110 and, in a real engine, MU-124. This is a read-size counter and source inspection, not a heap or out-of-memory measurement.

**The resource list is a bounded page with a continuation, and its overlay is read in windows (R14, revision 10).** `readResourceList` read every cached row of a kind through an unlimited index query, then every pending effect of the
account, and grouped them whole (the fifth review: 350 cached resources and 350 unrelated effects, one read of 350 rows and 350 effects), and neither it nor `useResourceList` had a page size or a cursor. It is now a **page**: `{ rows, next }`, at
most `limit` rows (default and largest `listPage`, 100: Q9; never below one, and the bound for anything that is not a number) after the cursor `after`, `next` being the cursor of the following page or null on the last. The page is a **keyset
walk** of the `kind` (or `parent_id`) index in primary-key order through the new `Reader.pageByKey` (rows whose index key is `key` and whose primary key sorts after `after`, optionally holding `match`, at most `limit`; the filters run inside the
store, so a skipped row is never returned), so a later page begins after the last row of the one before and a walk meets every row once however the list changes between pages (an offset would shift). A full page asks for ONE more row only to know
whether it is the last, so no read returns more than the page. The Dexie adapter filters during the cursor walk (a page after a deep cursor reads the rows before it without keeping them: its cost grows with the cursor, its retention does not;
a `[kind+id]` index would make it constant, at a cost on every cache write that nothing has measured, so none was added). The overlay is read only for the resources of the page, in **windows** (`plans/overlay-windows.ts`): a window of the
`resource_id` index is the first `queueWorkingSet` entries of the ids still unread, every resource before the last one in it is complete, and the last is walked by offset (the read is ONE transaction, so nothing moves under an offset) before the
lookup goes on with the ids after it. Each change is **folded** into a small per-resource state as it is read and dropped (`model/overlay.ts`: `foldEffect`, `applyOverlay`): per field of the patch (`label`, `archived`, each key of `value`) the latest
change by (`created_at`, `local_id`) wins, which is the sequential merge written so that the order the windows deliver the changes in does not matter, so what is held is a window plus one state per shown resource, never the queue and never
every change of one resource. A list item is therefore `{ base, merged, pending }`: the NUMBER of changes over the resource, not the rows (they are `readMerged`'s, `useCachedResource`; `readMerged` itself is a single resource's read and is unchanged).
Nothing is capped and no change is dropped: every change of every shown resource is read once and counted, and the effects of every other resource are never touched. `tests/data/overlay-fold.test.ts` (the fold against whole-population `mergeResource` over

### Device class, step-down and the floor

The first request uses `initialLimitUnconstrained` (4) when `navigator.deviceMemory` reports at least 8 GiB and `initialLimitOther` (1) otherwise; the absence of the signal
(Firefox, Safari) selects the lowest rung and is never assumed to be unconstrained. A step-down happens on a failure that a smaller page can help: an allocation failure, a
non-quota transaction abort, a watchdog overrun, or a durable crash-loop marker found at start. Quota exhaustion and an oversize response never step down. After `floorAfter` failures at limit 1 the engine stops with
`floor`, and the status model shows the floor state. Step-up is disabled (nothing specifies it). The crash-loop marker for pages of at least `markerMinBytes` is a
`localStorage` value written by `write-failure-marker.ts` and holds no account data (a test inspects every key and value written during the suite).

**The lifetime of the sizing marker (R42, revision 23).** `sync_state.sizing.attempt` says "a page of at least `markerMinBytes` was being processed and nobody has seen how that ended": the one signal of a tab that did not survive (killed for memory, frozen and discarded). It is a claim about an UNKNOWN outcome and must not outlive the moment an outcome is known, or the floor, which is reserved for genuine resource exhaustion, is reached by normal ends: three safe drops of a large page at the lowest rung (the persistence hold unavailable, a lapsed quota admission, another page owning the database) were `floor_hits: 3` and `stopped / floor` with no allocation failure, no watchdog overrun, no crash and no quota exhaustion. Exactly five things touch the marker: `recordSizingAttempt` writes it after the growth was admitted, bound to the attempt by an id; `commitPage` clears it in the transaction that lands the page; **`retireSizingAttempt` clears it when the engine SAW the attempt end without landing the page (a drop for any reason, `not_ready`, a lapsed hold, a failed commit, a run that was stopped meanwhile), and only if the marker is still that attempt's**, so an overtaken continuation cannot erase a newer attempt's; `captureRequest` consumes it at the next step (counted as a crash, or cleared without a count when this page names the attempt as one it saw end and could not retire); `resetSizingFloor` clears it with the count. No outcome record (`recordSizingOutcome`) touches it. A crash never reaches the retirement, which is what the marker is for, and a retirement that cannot be written is remembered in the page (`endedAttempts`, one id per account) and offered to the next capture, so a failing marker write never stops, loops or slows the engine; a retirement that failed and a page that reloaded before the next capture read the marker as a crash (the disclosed limitation). A marker is also left alone by a second page's own attempt: only that attempt's id retires it.

**An allocation failure at any stage of a page's processing is one signal about the device (R44, revision 24).** A page the contract allows goes through five places that can run out of memory, and each reports it the same way, as `allocation_failed` to the sizing policy: reading the body (`response.arrayBuffer()`), the scan (`scanSyncPage`: the two typed arrays of element offsets and node counts, their doubling for a page of more than 512 changes, the two trimmed copies it returns, and the decoding and parsing of a key, the `phase` and the cursor), the decoding and parsing of each element (`decodeChange`, inside the commit), a kind validator or deriver (registrant code, inside the commit), and the commit's own writes. The one definition is `isAllocationError` in `model/sizing.ts` (a `RangeError`); the scan, the element decoder and the validator guard each re-throw it instead of turning it into a verdict on the data, and the engine's `applyPage` takes the scan's to `sizingFailure` exactly as it takes the body's, while a decoder or validator failure inside the commit reaches `classifyFailure` (`alloc / range_error`), `commitFailure` and `sizingFailure`. Before, the scan's allocation errors reached the loop's own catch and stopped the engine as `local_storage` (the size unchanged, no floor count), and a decoder's were caught by a handler written for malformed data (`syntax / invalid text`, `PageInvalid / not_decodable`), so a valid page was asked for again at the same size and counted against the unrecognised-response budget. A malformed page keeps its classification (a `SyntaxError`, an invalid-UTF-8 `TypeError`, a `PageInvalid`, a validator's ordinary defect), a defect that is neither is still the loop's stop, quota is still quota, and the run, owner, generation, position and hold checks and the marker's lifetime (R42: a failed attempt retires its own marker, so a large page steps ONE rung) are unchanged. An obsolete run whose scan fails publishes nothing into the state of the run that stands, as for the body. Allocation failures are shown only as NAMED INJECTIONS at one site of the production code (`tests/support/data/allocation-faults.ts`): they test the handling of the exception, not a measurement of exhaustion on a device. Assessed and not changed: the body of an error response (`errorCode`, the outbox's `readBody`) is not a page, and an allocation failure reading it is the same counted read failure as the response.

### Quota

The quota guard keeps `quotaReserveBytes` free for `atlas-auth` and refuses user input only when the write itself would leave less than half of it; a cache page that would eat the reserve stops the engine with `storage_full`. The estimate is the
**origin's**, so it already includes other tabs' writes once it is read again, and the guard accounts for growth on **every** input path (R7):

* **the whole variable-size write counts, in UTF-8 bytes (R25, revision 13)**, never `.length` (UTF-16 code units: a CJK character is one unit and three bytes), and never the command alone. `draftWriteBytes` measures what a save puts in the stores: the canonical command and display patch (`draftBytes`); the header exactly as stored without the patch, so `defaults_context` (typed `unknown`, unbounded, persisted as `DraftRow.defaults_context`), `defaults_revision`, `endpoint`, `target_id`, `kind`, the identifiers and the dependencies are counted (`plainJsonBytes`, which measures what plain JSON carries and refuses, as a caller's defect, anything it cannot count exactly: a `Map`, a `Date`, a typed array, a class instance, a function, a `bigint`, a cycle, a nesting deeper than 256, **an accessor property**: a getter can answer differently when the write is measured and when it is stored). **It measures what the stored form can retain, not what iterating the value yields (R25, revision 14):** a structured clone keeps every own enumerable string-keyed property of an array as well as its members, so `Object.assign([], { previousAudience: "x".repeat(900_000) })` is a two-byte list to `JSON.stringify` and to a walk of its elements and a 900,000-byte value to IndexedDB (confirmed natively in Chromium, Firefox and WebKit by the reviewer). An array is measured by its own enumerable keys, never through its iterator (an instance can replace `Symbol.iterator`, which a clone ignores): the members it has, each hole as the `null` JSON says it is (counted in constant time, not walked), and every named property as an object's entry is, so the same measure serves the facade's estimate and the plan's check, for the context, the command and the display patch, nested at any depth; the `resource_versions` rows; every identifier again for the index entries and for the candidate rows the claim writes later (`IDENTIFIER_COPIES`, three copies on top of the header's own: the claim is not refused by the quota, so the save reserves what it will store); and 256 bytes plus the replacement's identifier for each dependant a supersession rewrites. The fixed 4 KiB allowance (`DRAFT_ALLOWANCE_BYTES`, the per-draft footprint reading's figure) stands for what has a FIXED shape only, and **no bound for an opaque or caller-sized field is ever inferred from it**. An edit replaces a header and a supersession deletes one, and neither credit is taken: the bound errs on the side of refusing early. A recovery copy's text is counted as two bytes a code unit, the encoding of the stored copy (unchanged);
* **what is reserved is a BOUND, and the plan enforces it (R25, revision 12).** The quota check is asynchronous and cannot run inside the transaction that reads the version bases, so the facade reserves an estimate made BEFORE it (`estimateDraftBytes`: for the command built from no bases and from the widest version for every target, the whole write as the transaction will compose it, the header included, through the SAME code (`composeDraft`) so the estimate and the plan cannot drift apart; the larger of the two, never less than the allowance: a request that cannot be built from either is a floor, not a claim that the write is small). The enqueue, edit and supersede plans then measure the WHOLE write they really composed, from the bases they read, against that bound (`maxBytes`) and write **nothing** when it is larger, reporting its size (`too_large`); the facade admits the write again at that size plus 1 KiB (`admitted`, at most three rounds, then a quota refusal), by the same overlapping-reservation rule. A command is therefore never stored at a size smaller than the one it was admitted at, for any builder, and an estimate that could not be made costs a second reservation, not a larger write than was admitted. The bound is the quota policy's input, not a measurement of what an engine allocates (compression and index overhead are not modelled);
* **what is promised and what has just landed is the ORIGIN's, not one page's (R28, revision 13).** The reserve protects `atlas-auth`, and the origin's free space is shared by every page, but `held` and the ledger below belonged to one guard's closure and production builds one guard per page: two pages over the same origin estimate each admitted a 900,000-byte save when the origin could hold one of them above the floor (the review's probe: 3,594,304 bytes left of a 4,194,304-byte floor), and a post-commit `data_changed` hint cannot prevent both being admitted first, nor can a re-read estimate that lags a write that has landed. The holds and the ledger of landed writes therefore live in ONE record that every page reads and changes atomically (`store/quota-ledger.ts`: `atlas-quota-ledger`, one record in one object store of raw IndexedDB, the only store whose read-modify-write is atomic across every page of the origin: overlapping read-write transactions on one object store run one after another). Every judgement and every settlement is ONE change of it (a hold ends and the landed ledger takes its bytes in the same transaction, so another page never sees them in neither). It holds two numbers and an expiry per entry and nothing else: no account, no content, no identifier of a person. It is opened on first use (constructing a guard holds nothing) and closed by `close()`. `createProductionQuota` builds the production guard over it (the application, the tests and the real-engine harness all use it); a guard with no ledger given shares the in-realm ledger of its estimate source, so two guards over one `navigator.storage` in one page agree (and claim no more than that);
* **a hold lasts as long as the write it admitted, and the write may begin only while it does (R28, revision 14).** A hold in the origin's ledger is LEASED (`quotaHoldLeaseMs`, 30 s), so that a page that dies with a save outstanding stops holding its bytes (they then count as landed for one estimate lifetime, revision 16); but a lease that simply ran out under a LIVE writer let every other page count the space as free while the writer was still to write into it, and counting the late write when it lands cannot undo the second admission (the review's schedule: the clock moved 30,001 ms while the first save waited just before its transaction, a second save was admitted, and both 900,000-byte bodies were written, 3,594,304 bytes left of a 4,194,304-byte floor). The two lifetimes are kept together. **The guard renews the lease of every reservation it still holds**, a third of a lease apart (one timer for the guard, cleared with the last settlement, never the thing that keeps a process alive), for as long as the reservation is unsettled: a page that dies, or is suspended, stops renewing, and its holds lapse, which is the dead-page reclamation. A reservation older than `quotaHoldMaxAgeMs` (10 minutes) is a leak, not a save, and stops being renewed. **A reservation says, synchronously, whether the write it admitted may still begin (`live()`)**: unsettled, still in the ledger, and not within the last third of its lease, so that a write that begins has a third of a lease to land while every other page still counts it. The writer reads it in the same synchronous step in which it decides what its transaction writes (inside the plan's decision, like the persistence hold's `valid()` and the synchronous eligibility checks that R26 and R27 added; `overBound` for a draft, `saveFormRecovery` for a recovery copy, `commitPage` for a cache page), writes **nothing** when it is `false` (`lease_lapsed`), and is admitted again, judged against everything that was admitted and written meanwhile (the facade, the recovery port and the engine each spend a bounded three rounds). A hold that was removed from the ledger is never revived by a late renewal: the writer is admitted afresh. What this cannot do is stop a transaction that was already running when its page froze or the machine slept: its bytes are counted when it settles (the landed ledger), or by the estimate once it shows them; a real freeze is not produced by any test here; **A hold with a living owner is never reclaimed for the want of a renewal (R28, revision 15).** The renewal and `live()` repair a writer paused BEFORE its transaction; they do not revoke or drain a transaction that has already passed `live()`: the review's schedule held A's 900,000-byte draft at the commit (`stall_commit`), moved the clock past the unmodified lease without running A's timers (a frozen page, a throttled tab, a machine that slept) and saved 900,000 bytes from a second account in room for 1,200,000: completing A's commit left 3,594,304 bytes of a 4,194,304-byte floor. Time cannot tell a page that is only suspended from one that is gone; a lock the page keeps can. Every hold of a ledger with **owners** (`HoldOwners`: in production a Web Lock per hold, `atlas-quota-hold:<token>`, kept by the writer's page; a model in the tests) is **claimed before it exists and given up after its settlement has been asked of the ledger** (so a hold that is in the record has an owner for as long as its writer can still write), is flagged `owned` in the record, and is **never judged by the clock**: it leaves the record only by its writer's settlement, or when its owner is PROVEN to have let go (the lock is released by the writer, or by the platform when its page is destroyed) and then its bytes LAND (below), they are not deleted. The proof is the one question the lifecycle matrix allows of a lock (`ifAvailable`, lint R2 still forbids `query()`): a `true` proves the lock could be taken, so its holder let go; a `false` proves nothing and **keeps the hold counted**, as does a lock manager that fails or a release the platform has not yet published (premise P-lock-b: it only delays a reclamation, never admits early). Owners are asked **only when a judgement refuses** (the ordinary save asks nobody), about at most 32 holds of other pages at a time (the rest stay counted; the next judgement asks about them), and the write is judged again with the proven ones gone; `check` never asks. A hold whose owner has gone is reclaimed AT ONCE, whatever is left of its lease (revision 14 kept it for up to 30 s), **and its bytes move into the landed ledger for one estimate lifetime (R28, revision 16)**: revision 15 deleted them, which let a page that had written and then lost its settlement, or died with a transaction committing, vanish from the account (next bullet). A ledger without owners (a ledger of one realm, an older double) and a hold without the flag keep the lease semantics of revision 14, with the same landing when the lease ends. A claim that cannot be made (the lock manager failed) admits nothing: the write would not be protected against a suspended writer. **What it does not do:** it cannot stop a transaction that was already running when its page was destroyed, nor say how many bytes it wrote (its bytes are counted by the landed ledger from the moment another page reclaims the hold, for one estimate lifetime, and by the estimate after that); a real freeze or crash mid-save, a throttled timer in a hidden tab and a lagging real estimate are not produced here (the free space and, in the one real-engine case with a moved clock, the observer's clock are named injections); a held Web Lock keeps a page out of the back/forward cache for as long as a save is outstanding (milliseconds), which is acceptable for a save. `tests/data/quota-owners.test.ts` (the guard over the model of the ledger: claim before the hold, release after the settlement, pre-transaction delay, in-progress commit, dead owner, lost renewal, a release that is not published, the leak, a failed claim, a lost answer, the bound on the work), `tests/data/outbox-quota-origin.test.ts` (the public `enqueue`, 67 schedules: five sizes and page counts x a healthy, an absorbed and a persistent ledger failure x three rooms, with a differential check that absorbed failures cost nothing, degraded-to-healthy, the stalled commit with the lease standing and expired, and a delayed completion), `tests/data/production-quota-owners.test.ts` (the real adapter over a model of Web Locks that throws on `query()`, and the real ledger over a model of IndexedDB), `tests/data/quota-cache-admission.test.ts` (the engine's page commit delayed past its lease with a living owner, and an admission the ledger could not answer), mutants MU-498 to MU-522 and, in a real engine, MU-523 to MU-526, and E-O6 in Chromium, Firefox and WebKit with real Web Locks and real IndexedDB (a page that closes frees the room at once, a page that stays open keeps its hold however far the other page's clock has moved, and a save that settles gives up its lock).

* **a hold is never deleted for the lack of its writer's word, and an age revokes only the permission to begin (R28, revision 16).** The review of revision 15 reproduced two schedules through the public `enqueue` (separate account databases, a fixed injected estimate that never shows a write, the production plans and facade, one writer held inside its commit). (1) **A completed write whose settlement does not reach the ledger:** both of its calls rejected, its lock released, and a healthy page proved the release, REMOVED the hold and admitted another body, because the bytes of the first had never entered the landed ledger (1,800,000 bytes retained in room for 1,200,000, 3,594,304 left of the 4,194,304-byte floor). (2) **An unfinished commit at `quotaHoldMaxAgeMs`:** the renewal treated every reservation that old as a leak, untracked it and released its lock, and the next page was admitted into a room the transaction was still going to fill (the same 3,594,304). The invariant behind both: releasing a lock, letting a lease lapse or losing a page says the writer stopped answering, never that it wrote nothing. **(a) Only the writer's own `not_written` (or a reservation whose writer cannot begin any more, below) takes bytes out of the account.** Every other end of a hold, namely a reclaim on proof, a lapsed lease, a settlement that never got through, moves its bytes into the landed ledger (`landHold`, the ONE place a write's bytes enter it, used by the writer's `written` settlement and by `liveAt` alike) against the figure the hold was judged on (`LedgerHold.base`; a hold of an older build that recorded none lands against the reclaiming page's own), where they count for one estimate lifetime and lapse with it. A write that never happened therefore costs the space for that long, and one that did is never forgotten. The landing is **once per hold** (`LedgerLanded.settled`, the latest 32 tokens), so a settlement repeated because its answer was lost counts nothing twice, and a writer that settles a hold another page already landed adds nothing. **(b) A settlement is published until the ledger takes it** (`conclude`): a rejected change is asked again at once, then offered again, paced (20 ms doubling to `quotaLedgerWaitMs`) for as long as one lease, and **the writer keeps its ownership throughout**, so the hold stands whole and no page can prove it over; a call that never answers is waited for (the ledger's own bound ends it). Only when the ledger has taken the change, the guard is closed, or a lease of offers has failed is the ownership given up, and the hold left in the record is then landed by whichever page next needs the room. **(c) `live()` returning `true` IS the writer beginning** (`Held.started`; it is read in the step that creates the transaction): from then on no time says the write is not running, so a begun reservation is never revoked by its age and keeps its hold, its owner and its renewals until the writer settles or its page is gone. A reservation older than `quotaHoldMaxAgeMs` whose writer has NOT begun is a leak: its permission to begin is revoked for good (`live()` is `false`) and its hold is taken out as the write that did not happen, which is exact (no landed debit), published like any settlement. The missing or throwing estimate stays `unknown` (a hold judged on no figure has nothing to cap and lands nothing), and the early `check` stays advisory (its memory of the ledger is aged once: a lapsed hold lands once and that landing lapses in its turn). **What it costs:** a page that dies without a word costs the room its hold had for five seconds after another page needs it; in a ledger WITHOUT owners (not production: Web Locks are a required capability) a page whose own lease lapsed finds its own hold counted against its re-admission for that long. **What it does not do:** it cannot know what a transaction that was running when its page was destroyed wrote, and it cannot show a real freeze, a crash mid-save, a throttled hidden tab or a lagging real estimate (the free space and, in the real-engine cases with a moved clock, the observer's clock are named injections); the estimate lifetime is the same provisional figure as before. `tests/data/quota-settlement.test.ts` (the landing arithmetic, the record, and a matrix of settlement outcomes by ledger behaviour (healthy, rejected twice, rejected until healed, silent until it arrives, one and two answers lost) by room, with the positive controls: a not-written settlement gives the room back at once, a written one is counted once, and with room for both nothing is refused; the destroyed, closed and given-up pages; the maximum age for a writer that began and one that never did, through the real renewal ticks at the production figures), `tests/data/outbox-quota-lease.test.ts` (the public outbox on all three growth paths) and `tests/data/outbox-quota-origin.test.ts` (the reviewer's two schedules, over separate account databases), `tests/data/quota-cache-admission.test.ts` (the engine's page commit), `tests/data/form-recovery-overlap.test.ts` (the recovery copy) and `tests/data/production-quota-owners.test.ts` (the real adapter over models of Web Locks and IndexedDB); in real engines the E-O6 cases "a completed write whose settlement the REAL ledger rejects stays counted" (a named fault on the ledger record's `put`), "the review's schedule in a real engine" and the two maximum-age cases (a named clock injection, the production renewal tick); mutants MU-527 to MU-545, MU-549 and MU-550 (unit) and MU-546 to MU-548 (real engine).

* **a reading of the estimate is as old as its request, and a landing is retired only when no reading that could lack it can still be judged (R28, revision 17).** The review of revision 16 reproduced a schedule through the public `enqueue` (separate account databases, the production plans and facade, a shared model of the origin's ledger; initial free space 5,394,304 bytes, the input floor 4,194,304, room for 1,200,000 above it): page A lands a 900,000-byte save, its debit expiring at 5,000 ms; page B samples the lagging estimate at 4,999 ms and is refused; at 5,001 ms B uses that SAME sample, the debit having been deleted, and is queued (1,800,000 bytes retained, 3,594,304 left of the floor, 600,000 below it). A request begun at 4,999 ms and answered after 5,000 ms is the same. The protection a landing gives belongs to the READING, not to the clock: a reading requested before the lifetime of a landing ended may lack its bytes for as long as it is used, whether it sits in the page's cache for another few seconds, is still on its way back from the browser, or was taken by another page. So **(1) every reading carries the instant its REQUEST began** (`Sample.start`), never the instant it was delivered; **(2) the cap applies while the lifetime stands** (`mayLack`: a reading that began before the entry's `until`); **(3) the entry is kept one further lifetime after `until`** (`liveAt`), the longest a reading that began before it can still be used; **(4) a reading that is older than a lifetime when the ledger judges it is not judged but asked for again** (`usable`, checked INSIDE the atomic change where the entries are retired, so a page is never judged against entries that have gone while it could still need them), and a reservation that cannot be judged on a fresh reading within its tries (`quotaLedgerAttempts`) is refused as `unestablished`, like one the ledger would not answer; **(5) a reading that began before `until` and is judged AFTER it is replaced, not capped** (`needsNewer`: a request made now shows the write, since the estimate is assumed to show a write one lifetime after it landed; the advisory `check` does the same, because its refusal stops the engine); **(6) `invalidate` and a settlement that landed bytes drop the request on its way as well as the cache** (an answer already promised to a waiting caller is still given, and never kept). The debit therefore lasts exactly as long as a reading that could need it; nothing is waited for its own sake. The approved `unknown` for a missing or throwing estimate and the input priority (cache refused before user input) are unchanged. Every consumer that grows the stores goes through the same guard (the facade's enqueue, edit and supersede, the recovery copy, the engine's page commit); `tests/data/quota-estimate-age.test.ts` (guard level, with a lagging estimate and a clock that can step), `tests/data/outbox-quota-estimate.test.ts` (the review's seam, all three growth paths, the recovery copy and the engine's page as the landing) and E-O6 in three real engines cover them.
* **a step of the wall clock is no proof that a written byte is reflected in the estimate (R28, revision 17).** The same review reproduced a second schedule: one millisecond BACKWARDS after A's save read as "this debit ends further ahead than its lifetime allows" and deleted a fresh debit at once (the same 3,594,304 bytes left). The pages of an origin share one clock, the wall clock, and it stays the one scale: **no page reads a corrected clock**, so no page reads another's stamps shifted and a repair made in one scale is never an error in another (`engine/quota-clock.ts`). What a step changes is what the guard CONCLUDES from a stamp, and that is repaired in the ledger itself, where every page sees it: **a stamp that ends further ahead than its lifetime allows is CLAMPED to one lifetime from the look that finds it** (never dropped, never believed, and written back, so the next look does not extend it afresh: `adjusted`, `repair`); **a page that finds a step FORWARDS takes every landed entry to have just landed for one lifetime of real time, and writes that back** (the step is found by comparing how far the wall clock and the page's monotonic clock moved between two readings, `quotaClockSlackMs` apart at the most; production passes `performance.now()`); a reading stamped after the clock went back has no age and is asked for again; a step found, in either direction, drops every reading. **Not claimed:** a step smaller than `quotaClockSlackMs` (250 ms: jitter and drift), and a step that a page with no monotonic clock (a test that names `now` alone, or `monotonic: null`; production always has `performance.now()`) lives through. A page that OPENS after a forward step is no longer a limit: revision 18 (the next two paragraphs) closes it. The clamp costs at most one lifetime beyond the look in which a backwards step is found; the distrust costs one more lifetime of real time after a forward step is found, and neither strands a reservation (an entry is retired one lifetime after its end, whatever happened to the clock). `tests/data/quota-clock.test.ts` and the R28b block of `tests/data/quota-estimate-age.test.ts` (forwards and backwards, ordinary expiry and room-for-both controls), `tests/data/production-quota.test.ts` (the production defaults follow `Date.now()` by `performance.now()`) and three E-O6 cases in real engines (a named clock injection: the real `performance.now()` does not move with it) cover it.
* **a page is not trusted with the age of a stamp it did not live through (R28b, revision 18).** The review of revision 17 reproduced the schedule that the revision's own tests had called a "documented limit", through the public outbox and in real Chromium: page A lands a 900,000-byte save (initial free space 5,394,304 bytes, the input floor 4,194,304, room for 1,200,000; its debit 904,961 bytes, five seconds), the wall clock moves an hour forwards with no real time passing, and page B's guard is then CONSTRUCTED; B queued another 900,000 bytes against the lagging estimate and deleted A's debit on the strength of its own reading of the stamp (1,800,000 bytes retained, 3,594,304 left of the floor, about 54 ms after the first landing), whether A was still open or not and whichever page reached the ledger first. A guard constructed after a step has no earlier reading of its clocks to compare, and nothing in a stamp shows what lay between it and now; "it expired" is therefore not a fact that page can know. **What a page can say is the reading from which its own clocks have been checked** (`QuotaClock.anchor()`: when the clock began, and again at any step it finds, in either direction; a wall clock that reads LESS than the anchor has been set back, with or without a second clock, and re-anchors it). **An entry stamped as landing after the anchor is believed as stamped; one stamped as landing before it is taken to have landed no earlier than the anchor** (`liveAt`, `reaches`): it caps the readings that began before one lifetime after the anchor and is retired one lifetime after that, so an abandoned debit is still recovered, within two lifetimes of the start of whichever page looks, and a debit is never forgotten by a page that cannot know how old it is. The view is the page's own and is never written back (a look must not extend an entry for the other pages, or two pages would extend it for ever; only a retirement the page is entitled to, a clamp and a distrusted extension are written). **The price, stated:** for the first lifetime after a page starts, a stale entry left by an earlier session caps its readings by the figure the entry's writer judged on (`min(estimate, base - landed)`); that is a refusal of input only where the cap leaves too little above the floor, it never lasts beyond the second lifetime, and **a refusal that only this view makes is flagged `unestablished`** (the page's lack of knowledge, not the space's): the sync engine asks again, paced, instead of stopping with a storage notice, and the advisory `check` stops nothing on it (it says `unknown`), while every writer (a save, an edit, a supersession, a recovery copy, the engine's page commit) is refused all the same, which is the reserve. A page that opens just after a landing is capped by it for a lifetime from its own start too (a control: the stamp's age is its to believe only from its own start). `tests/data/quota-new-page.test.ts` (149 cases: nine step sizes from none to ten hours, both directions, a page with and without a monotonic clock, the new page first / an original page that lived through the step looking first / every original page closed, the bounded recovery at each boundary, the estimate's readings across it, input priority, the approved `unknown`, the advisory fallback), `tests/data/outbox-quota-estimate.test.ts` (the same schedules through the public outbox over two account databases, every growth path, the recovery copy and the engine's page commit), `tests/data/quota-cache-admission.test.ts` (the engine asks again and does not stop), `tests/data/production-quota.test.ts` (the production factory over IndexedDB) and six real-engine E-O6 cases (a named clock injection and an injected estimate) cover it.
* **a recovery copy is admitted for what it stores, and nothing is created before it is (R33, revision 18).** The review of revision 17 found with the production port, plans and guard that the port sized only `snapshot.values` while it stored the form context, the tab id, the timestamp and the row's metadata too (a 900,000-character context and a one-character value were SAVED with 500,000 bytes of room above the floor), that **the claim of a writer generation wrote an empty terminal row, carrying that context, before the guard was asked** (so a refused save left it behind, and below the floor even an ordinary short context created a record), and that the port copied the caller's still-mutable snapshot after it had been admitted (a title changed from one character to 900,000 while the guard was asked was stored). **The whole row is sized** (`recoveryWriteBytes`: every string of the row at two bytes a unit, the order record at its widest, the form context three more times and the tab id twice for the primary key and the entries of the index on `form_context`, plus a fixed allowance that stands for nothing the caller sizes); **the capture is copied when `save` is called** (synchronously, with its place in the order, so a snapshot edited while the guard is asked or while an earlier save of the port runs is a later capture and not this one: what is admitted is what is written); **the claim creates no row**: it must be created at the call (R1: it is what orders the page contexts), so it writes only what is already there, an existing row's order record (a rewrite of what the row holds, not growth) or, for a form with no row, **one per-database counter** in the `sync_state` singleton (`form_writer_gen`, a fixed-size rewrite like `draft_seq`), from which the generation is taken, so two contexts that claim one after the other are still ordered by the transaction order and a context that has been refused still holds the generation it claimed. (**Corrected in revision 19, R1:** that was true only of a claim with no row; a claim of an existing row took `stored + 1` and did not move the counter, so the two kinds of claim were not one order. See REVISION 23.) A row is created only by a save that was admitted, and **a discard of a form that has no row (it would create one) is admitted the same way**: `saveFormRecovery` takes `mayCreate: false` and answers `absent` when the form has none, so the decision is made at the time of the write and not from the claim's answer, which is not true for longer than its transaction; with a row the discard replaces it with less and needs no room. When such a discard is refused, the writer remembers it (`Writer.cleared`), because nothing in the store can: a capture asked for before it is refused before it is written. What is already saved is never touched by a refused growth. **Departure, stated:** the review's two "sufficient space" controls (a 900,000-character context in 2,500,000 bytes of room, with a one-character value and with a 900,000-character value) are not admitted by this measure, which counts that context in the row and again three times as a key (about 7.2 and 10.8 million bytes); their intent, that room which suffices is not refused, is kept by controls sized by the same measure (`tests/data/form-recovery-quota.test.ts`, labelled `(adapted, revision 18)`), and the review's original probe files are preserved with their results. `tests/data/form-recovery-quota.test.ts` (the whole row, the boundary at exactly the figure, the first claim, a refused save, header growth, caller mutation, overlapping writers, a discard of a form with and without a row, the writer's memory), the adapted claim and overlap tests in `tests/data/form-recovery-overlap.test.ts` and three real-engine E-R3 cases cover it.
* **every growth that consumes the origin's space is admitted through it (R28, revision 14).** The audit of the plans that declare a quota class: `enqueueDraft`, `editQueuedDraft` and `supersedeDraft` (W2, W3, W4, input) reserve in the facade; `saveFormRecovery` (W9, input) reserves in the recovery port; **`commitPage` (W1, cache) now reserves in the engine, where the page is committed, for the size of the response it really is** (`admitAndCommit`): the revision-13 engine only CHECKED the largest page the limit allows before it asked, which holds nothing, so input saves made while the response was outstanding used the same free space and the page then committed without a growth admission of its own (the review's schedule: 19,513,344 bytes free, ten 1 MiB saves admitted while the response was held, 800 projections of 8,000 bytes then committed, 2,627,584 bytes left, below the 4,194,304-byte input floor). The early check stays, as a cheap refusal before the network; the admission at the commit is the authority. It is the same atomic change of the origin's ledger as the saves', so whichever comes second is judged with the first counted, and **the cache is the one refused first** (the page needs the reserve plus its own bytes, an input save only the floor): the engine stops with `storage_full` and the saves stand. The page's reservation is held through its commit and settled `written` only for a page that was applied; a refused page leaves no crash-loop sizing marker (the marker is written after the admission, inside the hold), so the next start does not read a refusal for want of space as a tab that did not survive. `writeDefaults` (W14, cache; WEB-12a) is server-sized (a B5 snapshot of up to 32 households of 100 members), so the defaults source reserves its bytes through the same ledger before it commits and the plan reads the reservation's `live()` where it decides; a refused or lapsed one writes nothing (the page keeps the snapshot in memory). `claimFormWriter` is a fixed few-hundred-byte row once per page context and form, and `writeProfile` and `recordDeviceVerification` (W12 and W13) rewrite fields of the singleton `sync_state` row in place (a name and a device id, bounded by the identity-body checks): none grows the stores by a caller-sized amount, and none is reserved; the allowance each save carries and the margin of the reserve cover them. `atlas-auth` itself is the consumer the reserve protects and is not asked;
* **a write is admitted only on accounting that counted every other page (R28, revision 15).** Revision 14 let a page whose ledger could not answer judge on its own accounting with the write counted twice (`degraded`); revision 13 on its own accounting alone, which counted another page's 905,000-byte promise as ZERO. The review of revision 14 showed that the doubled write bounds neither another page's outstanding write, nor the number of pages, nor the promise this page makes that no other page can see (independent `createOutbox().enqueue()` probes over separate account databases, a shared model of the origin's ledger and a fixed injected estimate: one writer held immediately before its transaction while another page's two ledger calls failed and it saved 400,000 bytes, 1,300,000 retained in room for 1,200,000; a degraded 400,000-byte writer that a healthy page could not see; three independent 900,000-byte saves that each lost both ledger calls, 2,700,000 in room for 2,000,000). No stand-in can: a blind page cannot know what another page promised, and nothing short of that knowledge keeps the reserve for every number and size of other pages. So **a reservation is admitted only on an answer of the origin's ledger, and refused when none comes.** A call the ledger REJECTS is asked again up to `quotaLedgerAttempts` (4) times with a short doubling wait (`quotaLedgerRetryMs`, 20 ms: 20, 40 and 80 ms between tries), so a transient failure of one tiny IndexedDB record costs a few tens of milliseconds and nothing of the guarantee; a call it does not ANSWER within `quotaLedgerWaitMs` (2 s) is abandoned (the change it was given is not applied late, and it is not asked again in the same call: a silence is not retried like a rejection), and there is no longer a lease-long "skip window" (every save asks the origin). Either way the refusal says **`unestablished`**: the facade and the recovery port report it as any quota refusal (`refused: quota`, the form stays open for a retry), but the sync engine does **not** stop with the storage-full notice for it (nothing is known to be full): it applies nothing, counts no failure and asks for the page again on its paced schedule, like a commit whose identity could not be verified. A hold a lost answer may have left is asked once to be taken out again (it is also reclaimable by proof, below); a call that is asked again does not count the hold its own earlier try made. **Distinct conditions, not conflated:** a missing or throwing ESTIMATE is still the approved `unknown` (nothing to protect; the write relies on its own failure and holds nothing if the ledger cannot answer), the advisory `check` of the engine still judges on what the origin last showed (it counts every promise it knows and refuses nothing on a guess: it is the cheap early refusal, and the reservation at the commit is the authority), and a refusal because the space is short is a refusal for want of space (not `unestablished`). **The price, stated:** a ledger that stays down refuses new saves even with ample room, and the text a person sees is the existing storage-full copy (the copy decision for a distinct message is Kieran's, with the visual and copy sign-off). The old stand-in's limit ("what a degraded page promises is invisible to the other pages") is gone with it: no reservation is made without the origin. A call that never completes is given up on by the ledger itself after 10 s, so it cannot hold up the calls behind it;
* a write in flight is **held** against the estimate (`reserve`/`settle`), so two saves near exhaustion are each judged with the other's bytes counted, in this page and in every other, and a refused reservation holds nothing;
* a write that landed makes the next check read the free space again, and its own bytes are **debited** for one estimate lifetime (and kept one more for the readings that began before it ended, revision 17) because `estimate()` may lag behind a write. The debit is a **ledger** of its own, kept apart from the cached estimate (R7, revision 6): the free space the first unreflected write was judged against, the bytes of EVERY write that has landed since, and the end of the latest one's lifetime, so a re-read is capped by `min(estimate, base - landed)`. The first revision took the debit from the cache at the moment of settlement, and settlement drops the cache, so two reservations in flight at once lost the second's debit (the second revision review: a constant lagging estimate of 6.5 MiB, two 1 MiB writes admitted and landed, a third 1 MiB write admitted though it would leave 3.5 MiB, below the 4 MiB floor). An estimate that does show the writes is never counted twice, and an invalidation (another tab's `data_changed`) drops the cache and nothing else;
* another tab's `data_changed` message invalidates the estimate;
* **enqueue, an edit that replaces a body, a supersession and a recovery save** all ask; discard and the dispatcher's own state writes do not grow the stores.

Successive large saves near exhaustion, a lagging estimate and a second tab are tested (`tests/data/quota-writes.test.ts`), and so are overlapping landings in every settle order, an invalidation or a refresh while writes are outstanding, the ledger's lifetime, two tabs over one estimate, and overlapping public enqueues (`tests/data/quota-ledger.test.ts`). The ledger is the ORIGIN's: another page's promises and landed bytes are counted from the shared record (`tests/data/quota-origin-ledger.test.ts`, over a model of it; `tests/data/quota-ledger-idb.test.ts` and `tests/data/production-quota.test.ts`, over the real record on a double of IndexedDB), whatever the estimate shows, and an estimate that lags a write that has landed cannot admit a second against the same figure. Revision 14 adds the lease (`tests/data/quota-lease.test.ts`: `live()`, the renewal, the lost hold, the retried and the degraded judgement; `tests/data/outbox-quota-lease.test.ts`: the review's delayed-save schedule on all three growth paths, the plans' `lease_lapsed` and the facade's bounded re-admission), the cache's admission (`tests/data/quota-cache-admission.test.ts`) and the recovery copy's (`tests/data/form-recovery-overlap.test.ts`). What no test here shows is a LAGGING estimate in a real engine (it cannot be made to lag on request) or a physical allocation. The write-ahead lease of `atlas-auth` still fails closed; the reserve is an **availability** question, not a way an authentication observation could be lost.
The reserve is an engineering default and **unmeasured**: P-Q measured the footprints, but Chromium's exact figure (CDP) did **not move** between the steady `atlas-auth` and the worst case of 100 fences and 200 leases (so what `atlas-auth` needs is below what that figure resolves), and Firefox and Safari report a
quantised or obfuscated estimate that says nothing at this scale. The number 8 MiB therefore stays a deliberately generous default: an over-large reserve costs an earlier refusal of cache pages, while an under-large one costs a failed lease. Lowering it needs the device roster and genuine exhaustion.
A real engine cannot be made to raise `QuotaExceededError` on request, so quota behaviour is shown only through named injection. The origin's ledger is the one exception to "only a model": its atomicity across real pages is exercised in three real engines (E-O6: two real pages with the production guard and the same injected estimate, with a slow-ledger injection that would let a change that is not one transaction through), while the free space itself stays a named injection, a physical allocation is not measured, and a real freeze or crash mid-save is not produced (a closed page is, and its Web Lock is released by the browser). The lease's renewal runs on the production timer (a third of the 30 s lease, never shortened): its logic is covered over fake timers and the double of IndexedDB, and E-O6 shows a hold's renewal visible to a second real page. Since revision 15 E-O6 also shows the ownership with real Web Locks and real IndexedDB in three engines: a hold is owned by a real lock named for its token (read by the TEST through `navigator.locks.query()`, which the application never calls), a page that stays open keeps its hold while the other page's clock (a named injection) says the lease is long over, a page that closes frees the room as soon as the browser publishes the release of its lock, and a save that settles gives up its lock.

## The outbox

### Enqueue and the version base

`enqueueDraft` is one `strict` transaction over `drafts`, `resource_versions` and `sync_state`, reading `cache`. It validates the request, resolves the
endpoint, takes each target's version base with an atomic read-increment-write on `resource_versions` (a draft of an untracked resource is seeded from the request), makes the
new draft depend on the latest unsettled draft against **each** of its targets (side effects included), assigns a per-database monotone `created_seq` (not the clock), and writes
the draft. The candidate `pending_effects` rows are written when the dispatcher claims the draft (`markInFlight`). The draft fence refuses an insert while a logout or retirement is pending. A draft is edited in place only while `queued`; discarding a
never-sent draft removes it and moves every direct and transitive dependant to `rejected`, retained; a superseded draft's row is deleted and the replacement takes its place in the
queue. **A replacement has a fresh identity (R24, revision 12):** a `localId` names ONE draft for its whole life, so `supersedeDraft` reads the draft under the replacement's key in the same
transaction that writes under it and refuses (`key_in_use`, nothing changed) when there is one: the old draft's own key, an unrelated draft's, a dependant's, one in flight (its body is frozen once
transmitted) or one retained after its answer. A retry of a supersession whose completion was lost (the old row is deleted by it) is recognised the way an enqueue's retry is: the old draft is gone and
the draft under the key IS that replacement (the same endpoint and targets, and the command the request builds again from the bases the draft holds has the digest the draft carries), so the answer is
`superseded` again with the dependants it paused, and nothing is written (and no quota debited). A replacement that was edited since, or another command that uses the key, is not the same save: `not_found`.
`enqueue` under a key that already names a draft never overwrites it either (it is that save's documented retry: `duplicate`). The draft row also records `bases` and `bumped`, so an in-place edit rebuilds from the same bases and a cascade recompute knows which bases are contributions.
**A supersession leaves the queue ordered (R45, revision 25).** The invariant is that every `depends_on` entry of a draft that can still be sent names an OLDER draft (a smaller `created_seq`) and that `created_seq` is unique at rest: the dispatcher holds a draft behind every earlier unsettled draft that shares a target and behind each of its dependencies, so a dependency that is newer than its dependant waits for the dependant while the dependant waits for it, and neither is ever sent. An enqueue cannot break it (a new draft is the newest). A replacement used to keep the old draft's `created_seq` whatever it now waited for: with a draft enqueued AFTER the old one for a target the replacement newly used (a changed target, or a side effect added), that draft was both the replacement's latest dependency (and its base counted that draft's contribution) and a draft the dispatcher held behind the replacement; the replacement was reported saved and the dispatcher went idle with `pick: null`, for every cause (a version conflict, an operation conflict, a defaults review). `decideSupersede` now decides the replacement's place: (1) nothing it waits for is newer than the old draft: it takes the old draft's place, as before, and consumes no sequence number; (2) something it waits for (derived, or named in `dependsOnExtra`) is newer, and no dependant of the old draft stands behind it: it takes the END of the queue, as an enqueue of the same request would (its bases already stand after every draft but its own dependants), consuming the next sequence number, and the plan writes the counter with it; (3) otherwise it is REFUSED (`order_conflict`) before anything is written, the old draft untouched: an explicit dependency on a dependant of the old draft (a cycle), a newer dependency with dependants that must stay ahead of the replacement, or a target the replacement raises where the old draft did not (a new target, a side effect added, a primary made version-checked) and a dependant of the old draft touches (the replacement's base would hold that dependant's own contribution). The plan reads the rows named by `dependsOnExtra` by key (windowed) because their place decides it. Two further rules cover the same boundary: a dependant is paused for review when the replacement leaves a different version for ANY id the old draft raised (another base, or none because the target or side effect was dropped: before, only a different base of an id both had paused it, so the dependant was sent on a version that will never exist), and a dependant that stays queued keeps the version record at what it stands on (before, the replacement's own result overwrote it, so the next save of the target was based on a version the dependant was about to raise; a paused dependant is resolved by the person, who supersedes or discards it, and both recompute from its bases). Tests: `tests/data/outbox-supersede-order.test.ts` (the pure decision, the production facade and dispatcher over the double of IndexedDB for the reviewer's twelve arrangements with a restart and ten minutes, the refusals with every store byte for byte as it was, and a seeded random program of 300 sequences that checks the invariant after every step and that every draft still waiting after the drain waits for the person), and the native `tests/e2e/fixture.data-supersede.spec.ts` (E-O7: twenty cases in each of three engines against real IndexedDB, with a restart). Unit mutants MU-736 to MU-750 and real-engine mutants MU-751 to MU-758.


### A save stores what it was admitted at (R39 and R40, revision 22)

`request.build` returns a graph the caller may still hold (the build contract gives the plan no exclusive ownership of it), and the plan used to digest and measure that object and then hand it on, by
reference, to a write issued one request at a time: IndexedDB clones a value when its `put` is **called**, and the header's `put` is awaited before the body's, so an edit made in that interval changed the
body after its digest and its quota admission were taken (the review: a 4,996-byte reservation, a 900,000-character stored command, the digest of another command, 904,978 bytes written, through all three
public paths in three engines). **Everything the plan derives is now taken from ONE private snapshot** (`snapshotPlain`, `model/snapshot.ts`), made once, at the instant the plan reads the build result
(`buildSnapshot`, shared by `planEnqueue`, `planEdit` and the supersession's recognition of a retry): the command, the display patch, the defaults revision and the defaults context are each read once (a
getter on the result answers once), copied deep as plain data (what a structured clone retains: own enumerable string-keyed properties, an array's named properties included) and validated; the digest,
the kind, the admitted size, the header and the body all come from that copy and the caller's graph is not read again. `bases` is handed to the builder as a copy. The **request** is copied as well, at the
public boundary before anything is awaited (`snapshotRequest`, the first line of `enqueue`, `editQueued` and `supersede`), so the endpoint that was validated, the targets that were read and the targets the
header stores are one value. Refused as `not_json` (a `TypeError`, as an `undefined` already was): a function, a symbol, a bigint, a non-finite number, a `Map`, a `Date` or any class instance, an accessor
(never run), a cycle, nesting deeper than 256 and **a sparse array**.

**A hole has one policy: it is refused (R40).** `canonicalJson` mapped over the members of an array and so skipped its holes (`new Array(1)` had the digest of `[]`; two holes made `[,]`, which is not JSON,
and `wireBody`, the body sent, is the canonical form of the stored command); `JSON.stringify` says `[null]` and a clone keeps the hole, so three readings of one value disagreed, and a supersession of the same
local id with a different command was recognised as the previous save. Normalising a hole to `null` would have to build an array as long as the hole list, where a refusal costs one property read, and an
`undefined` member was already refused, so the canonical form (`canonicalJson` throws on a hole) and the boundary (`snapshotPlain`) both refuse it. A genuine retry is still recognised; a dense `[null]` is still
a different save. **Two layers refuse a hole in the command, each shown on its own** (MU-684 and MU-690/691): at the public path either alone suffices, so no real-engine mutant of one layer alone exists;
the composed behaviour is the real-engine spec's, which fails on the revision-21 sources. **Not changed, and why:** a stored command from a build of this layer before this revision that holds a hole would
make `wireBody` throw (the dispatcher records an unanswered request); none can exist outside a developer's own browser, because this data layer has not been released and production does not start the
dispatcher (WEB-09b).

**The double of the store left the interval open on purpose now** (`tests/support/data/fake-idb.ts`): it applied every write of a transaction in one synchronous step and so could not show the defect; it now
has a turn between one write and the next, as the Dexie adapter's `await` per write, and an `afterPut` observer where the native `put` returns. `tests/data/outbox-snapshot.test.ts` pins that with a hand-made
plan that writes a graph the caller owns by reference (the edit lands between the writes), and the real-engine spec `fixture.data-write-snapshot.spec.ts` (E-S1, E-S2) has the same control through the real
adapter in every engine, so the protection is never a vacuous one.

### The dispatcher

`createOutboxDispatcher` sends one draft at a time (`maxInFlight` 1, decision D-18), oldest `created_seq` first, with the draft's `local_id` as the `Idempotency-Key` and the same
body on every resend. The queue is read through the `[status+created_seq]` index in turns of at most `queueWorkingSet` rows (**never the whole queue**, R6): the candidate test the plan uses to read a window (`candidateEligibility`) is held to the
`selectCandidate` oracle by a property test, a turn that finds no candidate carries its **scan progress** (`scanAfter`) into the next, so a long run of acknowledged or held rows is walked in bounded turns and never starves a sendable draft
behind it, and a pass that finds nothing is retried after `queueRescanMs`, doubling to 60 s and starting over on any event (`fruitlessCycles`). The bytes read per turn are measured, not argued (`idb.reads` read-budget statistics over a 5,000-row queue,
`tests/data/queue-working-set.test.ts`). Header rows (`drafts`) and command bodies (`draft_commands`) are separate stores (D-23, below), so a turn reads headers and loads one body, for the draft it is about to send. It sends only while the API-compatibility fact is `supported` (decision D-21): `unknown`
and `unreachable` hold quietly, `unsupported` and `missing` pause visibly, and the drafts are kept (`tests/data/outbox-dispatcher.test.ts`; I-O3 against the real `/health`).

What a command's answer means (`classifyAnswer`, `tests/data/outbox-answers.test.ts`, I-O1 and I-O2 against the released backend):

| Answer | The draft |
| --- | --- |
| `200` with an integer `revision` | a receipt: acknowledged, and its overlay is shown until a delta page publishes the resource |
| `409 conflict` (a stale `expected_version`) | `version_conflict`: only that draft pauses; an independent draft behind it is still sent |
| `409 operation_conflict` | the same key with a different body: `operation_conflict`, never resent |
| `409 defaults_changed` | the queue is held from that draft for review |
| any other `409` code | retained for a decision |
| `403 forbidden`, `400 malformed_request`, `404`, `422` **with an Atlas-formatted error body** | `rejected`, retained, never silently deleted |
| `503 slice_capacity` | capacity |
| `500`, `429`, `503`, an unrecognised answer, a `404` or a gateway page **without** an Atlas error body | still `in_flight`, retried with the same key |

A refusal is recognised only from an Atlas-formatted body (the rule the session applies to an activation): a `404` from a gateway is not the domain's refusal of this command,
and a draft is only ever rejected by the server saying so. A response that cannot be recorded is unclaimed (`not_sent`, `closed`, `not_covered`, `auth_state` do not count as an
attempt). A back-off starts at `backoffInitialMs`, doubles to `backoffMaxMs` with `backoffJitter`, and becomes a **paused** draft with an actionable "Retry now" after
`retrySustainedMs` of continuous failure; only `online` or "Retry now" resumes it, never another draft's success (I-O4 waits the full production duration).

A draft stopped by **local write failures** (R5, above) is not sent until its own "Try again". A draft whose commit was dropped because the persistence hold could not be had (`unverified`) is **not** a failed attempt: it is retried at a paced interval, counts
toward no budget, and does not pause the queue (`tests/data/engine-lifecycle.test.ts`, "a commit the persistence hold refuses", for the engine and the dispatcher alike).

### Related reads are bounded by a window (R21, revision 9)

The outbox keeps every change a person makes offline, so a target, a status or a review can be shared by any number of drafts, and no read may be bounded by that number. The reads of `src/data/plans/outbox.ts` that ask about a population now go through `src/data/plans/bounded-reads.ts`: **no single read returns more than `queueWorkingSet` (100) rows**, and a population that is only asked about is **reduced as it is read** (a count, a minimum, one or two stand-in rows) instead of held. A loop is bounded by the count taken at its start, never by its own bookkeeping.

* **The dispatcher** (`readDispatchWindow`) decides a candidate from the headers it depends on and, for each of its targets, **the earliest unsettled draft that has it** (`readEarliestSharing`; the rule only ever asks whether an OLDER draft that is not terminal shares a target, which that draft answers exactly), read a window at a time and **once per target per read**, however many of the 100 candidates share it (a conflict and 500 drafts behind it: 50,200 draft rows read for one window before; one walk of the target now). The paused, backing-off and defaults-review populations are **aggregated, not read as rows**: the number that need the person (each draft once), the number waiting out a back-off, the next wake and the lowest `created_seq` that holds the queue are exact over the whole queue.
* **Related drafts** (`TargetFold`, `src/data/model/related.ts`): what `planEnqueue` (what a new draft waits on: the LAST unsettled draft against each target) and `recomputeVersions` (the version base: whether any outstanding draft still targets an id, and the highest base among those that raised it) ask of "the other drafts that touch this id" is answered by at most two stand-in rows per id. `tests/data/related-fold.test.ts` holds them to the whole population over random populations, in any order and any windows; the same fold gives the dispatcher's `earliest`.
* **Cascades** (`discardDraft`, `supersedeDraft`, `recordOutcome`, `admitReceipt`) read the dependants of a draft through the `depends_on` index a window at a time. The members of a cascade are the atomic unit of the operation (every one is rewritten in the one transaction), so they are held, as **headers** (bodies are another store); what is bounded is each read, and the rollback is the transaction's.
* **Retry now for every retrying draft** (`resumeDrafts`) walks the drafts that carry a retry state a window at a time by keyset and **streams** the writes through the transaction's sink (`singletonPlan` gained `apply`, as `guardedPlan` has), in the SAME transaction, so what is in hand never grows with them.
* **The conflict inbox and the summary** (`readConflicts`, `readQueueSummary`) keep the oldest page and a count.
* **The drafts a local-write stop names** (R21, revision 10). `readDispatchWindow` bulk-read EVERY id that `stoppedDrafts` returned, from the durable `local_write_streaks` or from the fallback markers, in one call whatever `windowSize` was (501 stopped drafts: one 501-header read before candidate selection). `existingDrafts` (`bounded-reads.ts`) now asks a window at a time and reduces each batch to the ids that still exist before the next is read; the ids are what the dispatcher keeps (its stalled set and the `blockedUntil` map are as large as the stops), the rows are never held.
* **One resource the cache does not hold** (R21, revision 10). `readMerged` collected every queued and in-flight draft that targets such a resource into one array and joined all their command bodies (a new offline resource with 501 saved edits: 501 bodies in one call and 501 entries returned; the review reproduced it through the public `outbox.enqueue`, nothing seeded). It now folds the headers a window at a time into the OLDEST window of them (`OldestDrafts`, `model/related.ts`: at most `queueWorkingSet` headers, exact `total`, in `created_seq` order whatever order the store reads them in), so the create that introduces the resource comes first, and reads only that window's bodies. `MergedResource.creates` is that window; **`createsTotal` is the exact number of such drafts and `createsNext` the cursor of the next window** (the `created_seq` the window ended at, or null), passed back as `after` (`readMerged`'s input, `useCachedResource(id, after)`), so every saved change is reachable, each exactly once, however many there are, and none is dropped from the queue, sent late or counted wrongly: this bounds what ONE read returns and joins, not what is saved. A resource the cache holds reads none of its drafts or bodies. **The review's public probe asserted `creates.length === n`** (all 501 in one array), which is the unbounded result the finding reports; its intent (no saved change is dropped or made unreachable) is kept as `createsTotal === n` and a cursor that meets all `n` once, in a separately labelled adaptation (`.agtx/evidence/WEB-09a/regression/revision-10/final/reviewer-repro-r10-adapted/`), the original left byte-identical beside it.

`tests/data/outbox-bounded-reads.test.ts` runs every public path over a 501-draft population beside a five-draft control, with the double's read counters (the most rows one call returned, and the rows read in all) and a rollback for each atomic write; revision 10 adds both stop sources at 501 (durable streaks and markers), a stop that names a draft that is no longer there, a draft behind 501 stopped drafts, the whole dispatcher over them, and a new resource with 501 saved changes through the public outbox (the window, the exact number, every change reached once by the cursor, exact fills, a settled draft not counted, the whole dispatcher sending 120 of them in order), `tests/data/related-fold.test.ts` (`OldestDrafts` over 300 random populations) and `tests/data/hooks.test.tsx` (the cursor through the hook, on a mounted view). **Not changed, with the reason:** the consent digest (`summariseWork`, `setDraftFence`) is over every unsynced member by design (D-07: the ticket binds to the digest of the whole population), so it reads every header; `readMerged` returns the changes of ONE resource as rows by contract (R14), read a window at a time (`effects`, the admitted changes: unchanged here). These are fixture figures from a double of IndexedDB, not a measurement of a real engine's memory or of a device.

### The queue, as the person sees it (R6)

`createPagedQueue` shows ONE WINDOW of the queue at a time: the oldest `queueWorkingSet` visible rows from a cursor (the `created_seq` the window starts after), and **Show next changes** / **Show previous changes** (`SHOW_NEXT`, `SHOW_PREVIOUS`; proposed copy) move to the other window and REPLACE it (R6, revision 6).
The first revision's **Show more** raised a cumulative `limit`, so every refresh re-read, and the screen held, the whole expanded prefix. Now the window is the working set: what is held and kept live is `queueWorkingSet` rows, whichever window is shown, and the windows already visited are a trail of numbers (cursors), not rows. A refresh re-reads that
window (at most two chunks and the dependants' counts), never the rows before it; a window that has come to hold nothing (everything in it was sent or discarded meanwhile) falls back to the one before it. The counts in the header and the 200-entry warning are **exact counts** read through the `[status+created_seq]`, `review_block.kind` and
`retry_state.state` indexes, so a queue of any size is described correctly without being loaded. The watcher is lazy: a screen that does not show the queue reads nothing for it. Conflicts are read through their own index (`readConflicts`). Nothing is capped: every record stays reachable through the windows
(`tests/data/queue-working-set.test.ts`: 1,050 drafts forward and back, a refresh on the fifth window, a queue full of rows the tabs do not show, a window whose rows have gone; `tests/features/sync/screens.test.tsx` for the pager).

### Receipts

`admitReceipt` applies conditions 0 to 4 of the plan in order: 0, the draft is found with status exactly `in_flight` (a duplicate or late receipt changes nothing); 1 and 2, each
candidate row shows its display patch only while the cache is valid and no page has already mentioned the resource, and a row that would have been shown over a cache that is not
valid holds the draft instead; 3, the draft is acknowledged unconditionally (the operation committed whatever the cache is doing); 4, released rows leave, the draft leaves once
its overlay is gone and its flags are clear, and its dependants stop depending on it. It never writes `cache`: the overlay is shown until a delta page publishes the resource (release (a)) or the live edge shows that nothing will
(release (b)). Two real receipts and the real delta pages that follow clear the overlay (I-O1).

**The controller's lifetime (R29, revision 13).** `createDataEnv(deps, { start })` builds the controller and, by default, starts it at once (a caller that owns it: every test, the fixture). ## The verified profile and the device mirror

`GET /me` is read once per displayed `(account, epoch)` while online, through the stamped client, and kept only if its `id` equals the account. The username is shown **only
while it is verified for the current epoch**: a name is never inferred from the opaque account id and an older epoch's name is never shown for a newer one. It is held in memory
and written only when the account database already exists (`writeProfile` never creates it). I-P1 shows the real username in the rail and, with a proxy-rewritten `id`, that
nothing is shown until the person signs in again and the verified read is made for the new epoch. The device mirror (W13) records the device verification the same way.

**The two reads run inside the data layer's per-caller retry budget (R16, revision 12).** `followIdentity` (`src/data/engine/identity-task.ts`) runs each of them. The identity is a
**key, not an event**: the session publishes a new identity object at every evaluation and each request it sends makes more of them (its lease hints reach every tab), so a
notification for the `(account, epoch)` already being worked on does nothing, and only a different one starts work. A read that could not finish is asked again **on a timer**,
by the retry table's rules (plan 5.6): network, time-out, `5xx`, `429` and `408` back off (2 s doubling to 60 s, +/-20 %) and pause once the failure has lasted `retrySustainedMs`;
three consecutive unrecognised answers (any other status, a `200` with no usable body) pause that caller, and `online` does not end that pause (only the caller's own `retry()`
does, and no screen offers one yet); `not_sent`, `not_covered` and `stale` are asked again a few times on a short bounded schedule (`notSentBackoffMs`) and never counted;
`closed`, `closed_unresolved` and `auth_state` wait for an event and are never counted. The production adapters (`src/data/ui/identity-reads.ts`) classify; nothing flattens a
failure to `null`. With the account's database open the counts live in `sync_state.read_retry_states["profile:<epoch>"]` and `["device:<epoch>"]`: the entry belongs to **one
sign-in** (a new epoch is new work and is held by nothing of the earlier one; writing a family's entry drops the family's other entries, and a success leaves none), a reload does
not restart the sustained-failure clock (a page that starts while a back-off is under way waits its first step), and a second tab shares the pause. Without a database the
page's memory counts, and what it knew is folded into the durable entry (`known`) in the same transaction when the database first opens. The healthy path writes nothing.

**The budget is established before anything is asked (R16, revision 9).** The first version let the profile request go while the controller was still attaching the account's database (its runtime loads lazily and the database opens a moment later), so a reload or a remount supplied one request that the stored, paused budget forbade, and the report relaxed its own assertion to allow it. Now the controller says whether it has finished LOOKING for the account's database (`databasePending`: it is not pending once it has opened the database or learnt that there is none, and a notification of the identity it is already looking for does not start the look again, so it can finish; **a look that FAILS is not an answer**, see the next paragraph), and **a caller asks nothing while the look is under way**: the durable entry is read first (and a budget that cannot be read asks nothing and looks again a few times, uncounted). A durable pause is honoured from the first moment (zero requests across repeated remounts, with the database listing held for 1.5 s in three real engines: E-C11), a database that exists but is not paused is asked as before, and a database that does not exist is asked on the page's memory once the look has finished. The inverse schedule is closed too: what a page counted before its database appeared, a **pause included**, is written when it does (`persistReadRetry`, a guarded plan that folds the page's memory into the entry without recording an outcome), because a paused caller asks nothing more and no later outcome would ever write it. Cost, stated: the account label is no longer asked for before the look finishes, which in production is the lazy chunk's load and one listing of the databases; in WebKit with a deliberately held listing it is about 4.8 s, because Dexie's own Safari workaround polls the listing every 100 ms until it resolves.

**A look that FAILS is not an answer (R16, revision 10).** `attach` finished its look when the runtime chunk did not load or when the listing or the open rejected, so with no bound database the profile read began with an EMPTY in-memory budget even over a database that holds a durable pause, and every remount repeated it (the review's unit probe: nine `/me` requests over three mounts, for a rejected `open()` and for a rejected runtime load alike; natively, `indexedDB.databases()` rejecting with `UnknownError`: six over three pages in each of Chromium, Firefox and WebKit, with the controls passing). The opener already distinguished a failed listing from absence (`openAccountData`: "an unknown answer is never absent"); the controller had lost that distinction. Now:

* **a failed look is an explicit, retained state** (`lookFailed`): whether the database exists, and what budget it holds, are unknown, so the identity readers keep waiting (`databasePending` stays true) and ask nothing, whatever the budget turns out to be, and a remount starts the same way;
* **it is visible and recoverable, boundedly:** the screens read the failure meanwhile (`queue`, `conflicts` and `summary` say they could not be read: no change from before), and the look is made again at the facts' re-read pace (`factsReadRetryMs` 250 ms doubling to `factsReadRetryMaxMs` 10 s, then one attempt per 10 s for as long as the failure lasts), at once on `online`, on another tab's `atlas-sync` hint and on the person's own "Try again" (`retryLoad`), never on every notification of the same identity (the session publishes one at every evaluation), never for an account the page has left (an identity change or sign-out forgets the failure and its timer) and never after the controller is disposed. The look is local (a listing, a chunk): it asks the network for nothing, and it is the only thing a failure schedules;
* **genuine absence is still an answer** (`absent`: the page's memory is the budget, three unrecognised answers pause it, nothing is created), and so is a refusal because the identity moved; **a successful look** (opened) reads the durable entry and honours it, a pause by duration or by three unrecognised answers and a durable back-off alike, and offline hydration of a persisted verified name follows once the database binds.

**What a look found belongs to ONE binding (R16, revision 11).** `lookedFor` (the answer of a finished look: the database opened, or there is none) survived the binding it described. After the service ended, after the page left the account and came back, or at the start of a new look, `databasePending` still said "nothing left to discover" while the new look was pending or failing, so the profile task started without reading the current durable budget (the review's two probes: three `/me` requests over a saved pause when the reopening rejects, and one before the binding when it succeeds). The answer now ends with the binding it described (`unbind`: the service ended, was replaced or left for another account) and with the START of any later look (`attach`), BEFORE the readers are told; only a look that lands (`finishedLooking`) says again what is there, and a look that fails leaves the account unknown (`lookFailed`, as above). **Nothing looks again by itself when a binding ends**: a reopening would undo the latch of a wipe that closed it (`openAccountData` sets the latch back to `open`), so the identity's next notification, `online`, another tab's hint and `retryLoad` do (the session republishes the identity at every evaluation, so the wait is short in production). The durable budget is never reset or ignored to restore progress. `tests/data/ui-env-binding.test.ts` (the service closes and the sign-in moves on, with reopening rejecting, paused, healthy and absent; the look delayed; A, B, A with B failing or absent; an absent answer followed by a failing look; a read that is backing off when the service ends), mutants MU-344 to MU-346.

**An opened result is admitted only while its service is live (R59, revision 37).** The review of revision 36 held a real `DataRuntime.open()` result at the asynchronous seam and closed its service before the controller received it: `attach` looked only at the result's kind, bound the dead service and declared the look finished (`lookedFor`), so `databasePending` said "no database" while `openServiceOf` had no live service to give, and the profile reader took its in-memory path over a database holding a durable pause (three `/me` requests in 65 s; natively one in a second, in each engine). Its end had already been announced, so no `onEnd` undid the binding, and a hint could not either (`reprobe` opened only with no binding). Now (1) an `opened` result whose service is not live is a FAILED look, exactly like an open a closure refused (R37): nothing is bound, no facade is made, the screens say they could not read, and the look is made again on the paced schedule (or at once by a hint, `online` or `retryLoad`); its next open is refused or authorised as the latch then says, so no wipe's latch is overridden by the page. (2) Absence is known only when the look for the account FINISHED and bound nothing: `databasePending` is true while a binding stands whose service is no longer live (the window between a latch and its end), so the readers wait rather than read absence into it. (3) `reprobe` looks again when the binding that stands is no longer live, as `follow` does. A binding that ends after it was made unbinds on its end as before, and nothing reopens by itself (a wipe's latch must not be undone by the page). `tests/data/controller-late-binding.test.ts` (the production controller over a real `DataRuntime`: a closed and a latched result, every result dead, retry, hint, a later end, the second layer); the review's native diagnostic, adapted only in its paths, passes in three engines.

**An identity read is admitted only by the binding that stands in the turn that asks (R59, revision 38).** The review of revision 37 let the profile's first `/me` fail (the production 2 s back-off), then closed the bound service while the retry was crossing its budget adoption: `adopt()` answered `adopted` from its cached shortcut (awaiting even that yields), the controller unbound the service and cleared its look, and the stale answer reached `readMe` with no live binding (in the model and in Chromium, Firefox and WebKit). `followIdentity` (`src/data/engine/identity-task.ts`) now decides admission synchronously immediately before it runs the reader (`bound`): a live database whose budget the work has taken in admits; one it has not (it opened late, or replaced the one taken in) is read first; none while the page has not finished looking (a binding that ended is unknown, not absent) waits for the controller's notice; none after a finished look (a genuine absence) keeps the memory path (the profile's memory-only verification). Connectivity and the identity are read in the same turn. Every awaited answer is taken in only while the binding it was given for still stands: a budget read or its persistence delivered after its database ended or was replaced is `stale` and not adopted; an outcome's durable record marks the work adopted only over the database that stands. A reset decided before an awaited write (`online`, "Retry now") is applied only if no outcome was counted and no other budget was taken in meanwhile (a newer back-off, or another page's newer pause, stands); a binding that merely ended does not cancel it. Nothing here opens a database or shortens a back-off: a binding event wakes a waiting attempt, and a pending timer is never replaced by a sooner one. An adoption that answered yet left the standing database's budget not taken in is never retried at once (the short, bounded schedule, then an event), so the read-again-and-adopt cycle cannot spin without yielding (driver-r38b found that MU-205, an adoption that never reads, made it a microtask loop). **A body that is not the contract's is never a verification (R18, revision 9).** A `200` whose body is not the contract's is an UNRECOGNISED answer (counted; three in a row pause the caller; the history stays until a valid success; a repaired answer verifies), not a success: `parseAccountIdentity` and `parseCurrentDeviceId` (`src/data/model/identity-bodies.ts`) check what each consumer uses, at the adapter (`readMeThrough`, `currentDeviceThrough`) and again in the consumer. **An offline start shows the persisted name (R17, revision 12).** The controller loads its runtime and opens the account's database a little after the profile source

the current epoch is shown with no request, one persisted for another epoch is not, and an identity that moves while the read is pending shows nothing of it. A name verified

## The sharing defaults and the defaults review (WEB-12a)

*Added by WEB-12a, 10 October 2026. The consumer contract is `docs/sharing.md`.*

* **The record.** `GET /defaults/snapshot` (B5, in the pinned contract `0.27.0-rc.1`) returns the resolved defaults and the households their revision covers, from ONE database snapshot. `model/sharing-snapshot.ts` parses it strictly (`parseSharingSnapshot`: every key, bound and pattern; no extra keys; ≤32 households, ≤100 members) and `plans/defaults.ts`'s W14 `writeDefaults` stores it whole as `DefaultsRecord { format: 1, snapshot, fetched_at, issued_at, epoch }` in `sync_state.defaults`, never combined with a separately timed read. W14 carries the guard set of a response-derived write (INC, CLS, EPO, plus the service's G1, G2 and G5 hold), never creates the database, and keeps a stored record issued LATER than the incoming one (two pages' reads landing out of order). The stored field is read tolerantly (`readDefaults`): WEB-09a's `null` seed, another format or damage is "no record".
* **The source.** `engine/defaults-source.ts` follows the identity like the profile source (`followIdentity`, caller `defaults`, the per-caller budget of plan 5.6) but only while a screen USES the defaults (`DataEnv.defaults.use()`, which `useSharingDefaults` calls): nothing is asked on the boot path or by a page that never shows sharing (D-12a-10). `refresh()` is one read now for a person's act (an editor or a review opening, a save that moves the revision), uncounted. Memory belongs to one `(account, epoch)` and is forgotten on any identity change; a late answer for an earlier identity is dropped; a body that is not the contract's snapshot is unrecognised (counted, never kept).
* **Capture.** `captureDefaults(record, kinds)` (pure) is what a queued create attaches: the revision for `defaults_revision`, and per template kind the template with every household it names from the SAME snapshot (`defaults_context`, format `atlas-defaults-context-v1`). With no record it is `never_fetched`; a named household the snapshot does not list is captured `unavailable`. Both put the kinds in `defaultsReview`.
* **`BuildResult.defaultsReview`.** A non-empty list stores the draft with `review_block { kind: "defaults", kinds }`: the dispatcher never claims it (`markInFlight` refuses a review block) and the queue is held from it (D-19), exactly as for a draft refused with `409 defaults_changed`. On an EDIT the field decides the block: absent keeps it (an edit of the content is not a review of its audience), `[]` clears it, a list replaces it. A non-list is `not_json`.
* **`Outbox.confirmDefaultsReview(localId, { reviewed, defaultsRevision, defaultsContext, replacementId? })`** is the person's confirmation in the review, and the only thing that releases a defaults review: it reads the draft, its body and the basis of each target (`readReviewDraft`, read-only), rebuilds the stored command with ONLY its top-level `defaults_revision` replaced and its context replaced (`model/review-confirmation.ts`), and goes through `editQueued` (a queued draft blocked locally: same `local_id`) or `supersede` (a draft refused with `defaults_changed`: a fresh `local_id`, `replacementId` on a retry). The build refuses versions other than the draft's stored bases (`rebuild_refused`): a body this layer did not author is never sent on a version it was not composed against. `DataActions.confirmDefaultsReview` routes it to the leader's facade when one is attached, so its dispatcher wakes. **It is conditional on the draft the person reviewed** (WEB-12a review cycle 1, R2): `reviewed` is the row the review showed (`reviewedOf`: its body digest, revision, captured context, review block and status). The facade compares it with what it read, and the rebuild's request carries `EnqueueRequest.expectDraft`, which `planEdit` and `decideSupersede` call with the draft as stored INSIDE the writing transaction; a draft that changed in between (another page's `editQueued` of the same queued draft, a changed block or context) refuses the confirmation with `draft_changed` and nothing is written, so a committed edit is never overwritten by a body built from the earlier read. `expectDraft` is generic (`EditOutcome` and `SupersedeOutcome` gain `draft_changed`) and only a caller that decided on an earlier read needs it.

## Retry budgets this slice owns

Four of the seven classes of the reconciliation (`src/data/model/retry.ts`): network or 5xx on a draft submission, network or 5xx on a read, unrecognised responses on a read
(three consecutive ones stop the caller, durably), and a local write failure that is not a quota (three stop **that operation**, durably, per operation: R5). The three recovery-scoped classes are WEB-09b's and nothing in
`src/data` writes them. `not_sent`, `not_covered`, `closed`, `stale` and `auth_state` increment none of these. A back-off is duration-based and its clock is durable, so a
reload does not restart it. Two ordinary callers use the read classes since revision 12: the profile read and the device mirror (the section above), each keyed by sign-in
(`profile:<epoch>`, `device:<epoch>`) in `read_retry_states`, and WEB-12a adds a third, the sharing defaults (`defaults:<epoch>`, only while a screen uses them); `recordReadOutcome` takes `known` (what the page already counted) and `supersedes` (a caller family keyed by
sign-in), and `readReadRetry` is the read-only plan that reads an entry.
