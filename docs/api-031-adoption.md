# API 0.31 contract adoption

The client targets the published Atlas API 0.31.0 contract, package v0.31.0-rc.1 (backend `7dc51e39`, contract SHA-256 `c43796e6…e848`). `contract-pin.json` identifies the exact backend commit and downloaded archive; `contract-release-verification.json` binds the public release/tag, checksums and source verification. Health compatibility remains the existing strict rule: >=0.31.0 and <0.32.0. Existing lower/upper rejection and malformed-version checks remain.

Compared with the actual API 0.29.0 release, API 0.31 adds two online-only reads and 9 schemas, and removes no path or schema (76 paths become 78, 191 schemas become 200):

- `GET /occurrences/{id}/dependency-graph` (`getDependencyGraph`, BE-DEPENDENCY-GRAPH): the caller-authorised upstream prerequisite graph of one occurrence, with `DependencyGraph`, `DependencyGraphNode`, `DependencyEdge` and `DependencyGraphTask`. It is not part of `/sync` and carries no completion authority.
- `GET /people/{id}/activity` (`getPersonActivity`, BE-PEOPLE-ACTIVITY): one page, newest first, of metadata-only events about a person and its fields, with `PersonActivityPage`, `PersonActivityEvent`, `ActivityTarget` and `ActivityAccount`. Every read applies current access; it is not part of `/sync` and is never cached.
- Bounded `/sync` (BE-Q23): an optional `max_changes` query parameter (4 to 800) bounds the changes in one response. Absent, responses are unchanged. With it, a snapshot page holds at most `min(limit, max_changes)` resources and an oversized delta revision arrives as segments, one per response, marked by the new optional `Batch.segment` (`BatchSegment`: `index`, `last`) and followed by a continuation cursor; clients stage segments and apply the revision only when the last arrives.
- Page bound (BE-B1): `SyncPage.batches.maxItems` rises from 80 to 200, the `limit` maximum; the `limit` and `readSync` descriptions now state the unit per phase. No accepted request changes its answer.

Only `Batch`, `SyncPage` and the `/sync` operation change among existing definitions. The backend numbered these steps 0.29.1 (dependency graph), 0.30.0 (bounded sync), 0.30.1 (their combination), 0.30.2 (People activity, recorded on its branch as 0.29.2 and re-sequenced at integration) and 0.31.0 (page bound); none of the intermediate versions was published, so every server this client supports carries all of them. The backend's `docs/api.md`, `docs/sync.md`, `docs/tasks.md` and `docs/people.md` at `7dc51e39` describe the obligations.

Importing types implements none of these: production still never sends `max_changes` (`DATA_CONFIG.segmentedMinApiVersion` stays `null`; `model/segmented-sync.ts` was written against BE-Q23's provisional contract and its consumer task owns reconciling it with the published one), and no screen reads the dependency graph or the activity timeline yet. Those journeys, their reviews and frontend release acceptance belong to the consuming tasks.

Current fixture health responses, compatibility expectations, preview/packaging checks and optional PostgreSQL backend image follow the new pin. Existing partial session test doubles remain partial. Historical 0.27/0.28/0.29 measurements, integration runs and review reports retain their original attribution and do not become API 0.31 evidence; the development-pair diagnostic policy for the approved 0.30.0 executable is unchanged.

Active tasks may retain their previously verified published pin while finishing a frozen campaign. Adopt accepted contract changes at an idle authoring boundary, preserving prior evidence and checking the applicable integration paths.
